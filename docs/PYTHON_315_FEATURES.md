# Python 3.15: применимость к AL Torrent Tools

> Обновление решения, 13.10.2026: для основного проекта выбран прямой переход
> на обычный CPython 3.15.0. Ниже сохранены результаты и состояние завершённого
> эксперимента; прежнее решение оставить 3.14 относится к его моменту. Текущие
> изменения и проверка рабочего образа — [PYTHON_315_MIGRATION.md](PYTHON_315_MIGRATION.md).
> Переход на 3.15t и экспериментальный HEVC-пул не принят.

Проверено 13 октября 2026 года. [Python 3.15.0 выпущен 9 октября как stable](https://www.python.org/downloads/release/python-3150/). Эта записка оценивает возможности версии; решение о миграции зависит от отдельной проверки совместимости и сравнительных измерений.

## Внедрённое улучшение: явная диагностика через Tachyon

Новый стандартный пакет `profiling` описан в [PEP 799](https://peps.python.org/pep-0799/). Для проекта добавлен `backend/scripts/profile_runtime.py`: оболочка над официальным CLI `profiling.sampling`, без импортов приложения, обращения к БД и новых зависимостей. Она работает только по явному запуску с PID уже существующего локального процесса. Worker, API и Docker не включают профилирование автоматически.

Это полезно для расследования задержек `worker.py`, `job_runner.py` и `file_hasher.py`: сопоставление wall и CPU помогает отличить ожидание qB/HTTP/диска от обработки Python, а GIL-профиль — проверить конкуренцию потоков. Это диагностическая возможность, а не заявленное ускорение приложения.

Примеры из `backend/`; `12345` нужно заменить реальным PID процесса в том же пространстве PID, запущенного под CPython 3.15. Для Docker оболочку запускают внутри нужного контейнера, где виден целевой PID.

```sh
python scripts/profile_runtime.py attach 12345 --duration 30 --mode wall --output /tmp/altt-worker-wall.bin
python scripts/profile_runtime.py attach 12345 --duration 30 --mode cpu --output /tmp/altt-worker-cpu.bin
python scripts/profile_runtime.py attach 12345 --duration 30 --mode gil --output /tmp/altt-worker-gil.bin
python scripts/profile_runtime.py dump 12345 --async-aware --output /tmp/altt-worker-stack.txt
python -m profiling.sampling replay --flamegraph -o /tmp/altt-worker-wall.html /tmp/altt-worker-wall.bin
```

Оболочка проверяет CPython 3.15+, PID > 0, существующий каталог результата, duration 1–300 секунд и rate 1–10000 samples/sec. По умолчанию: 30 секунд, 1000 samples/sec, binary, все потоки. `--async-aware` выбирает цепочки `await` и допускается только с wall; он заменяет режим всех потоков. Выходной файл создаётся с правами `0600`; существующий файл, каталог и даже оборванная символьная ссылка не перезаписываются. Ошибка профилировщика и прерывание не публикуют частичный результат. У дочернего диагностического процесса есть таймаут; целевой процесс оболочка не останавливает.

Для доступа к памяти процесса могут потребоваться права ОС. Оболочка не запускает `sudo`, не меняет системные настройки, не включает blocking sampling и не захватывает другие PID автоматически. Аргументы и ограничения проверены по [документации CLI](https://docs.python.org/3.15/library/profiling.sampling.html) и [исходнику CPython v3.15.0](https://github.com/python/cpython/blob/v3.15.0/Lib/profiling/sampling/cli.py).

Sampling даёт статистическую картину. Для migration gate измеряются непрофилируемые процессы: profiler сам потребляет CPU/память на том же хосте. Снятые отдельно wall/CPU/GIL-профили нельзя трактовать как точные сравнительные времена.

## Кандидат после измерений: точечные lazy imports

[PEP 810](https://peps.python.org/pep-0810/) добавил `lazy import` и совместимый со старым Python `__lazy_modules__`. При ленивом импорте ошибки и эффекты загрузки сдвигаются к первому использованию.

Пока изменение не внедрено. В `mediainfo.py` необязательный `pymediainfo` уже загружается внутри функций с обработкой `ImportError`. В `api/rest.py` импорт регистрирует обработчики джобов, а SQLAlchemy-модели и ASGI-маршруты также требуют предсказуемой инициализации. Глобальный `PYTHON_LAZY_IMPORTS=all` создаёт риск изменения порядка регистрации. Для постоянно работающих сервисов сокращение старта само по себе не доказывает снижение ресурсов после прогрева.

Условие возвращения к кандидату: профиль импортов показывает дорогую необязательную ветку; точечный патч улучшает повторяемый startup/RSS; тесты подтверждают неизменность регистрации, первого запроса и ошибок отсутствующей зависимости. Новый синтаксис до принятия миграции не используется.

## UTF-8 по умолчанию: аудит поведения

[PEP 686](https://peps.python.org/pep-0686/) сделал UTF-8 mode стандартным в 3.15. Это изменение поведения при неявной кодировке, а не оптимизация ресурсов.

Проверка кода показала:

- `.env` parser, чтение build stamp, heartbeat бота и probe-файл cleanup уже задают `encoding="utf-8"` явно.
- `.torrent`, BLAKE3 и Matroska EBML используют бинарное I/O; их байты новая текстовая кодировка не меняет.
- `_mediainfo_cli_version()` использует `subprocess.run(text=True)` без encoding. Он читает только `mediainfo --Version`, стандартный вывод версии — ASCII; ошибка декодирования уже приводит к отображению ошибки. Подтверждённого дефекта не обнаружено, код не менялся.

DB naive UTC, формат браузерных дат и `app.utils.datetime_fmt.utcnow()` остаются прежними. Новый Python не служит основанием изменять эти контракты.

## Возможности, которые не стоит внедрять без отдельного основания

- [`frozendict`, PEP 814](https://peps.python.org/pep-0814/): для существующего каталога джобов уже есть tuple и frozen dataclass. Замена изменяемых JSON payload на другой тип нарушила бы ожидания `isinstance(..., dict)` и библиотек без доказанной пользы.
- [`sentinel`, PEP 661](https://peps.python.org/pep-0661/): в production-коде не найдено самодельных `object()` sentinel. Замена существующей семантики `None` потребовала бы изменения контрактов, которого задача не требует.
- [Unpacking comprehensions](https://docs.python.org/3.15/whatsnew/3.15.html#pep-798-unpacking-in-comprehensions): сокращение записи само по себе не улучшает эксплуатацию; переписывание циклов ради синтаксиса не выполняется.
- [JIT](https://docs.python.org/3.15/whatsnew/3.15.html#upgraded-experimental-jit-compiler) остаётся экспериментальным. Он отдельно влияет на скорость и память; опубликованные средние ускорения не переносятся на ALTT. Его нельзя молча включать только в одном участнике сравнения.
- [Free-threaded ABI](https://docs.python.org/3.15/whatsnew/3.15.html#pep-803-stable-abi-for-free-threaded-builds) расширяет возможности C-расширений; обычная миграция GIL-on не делает потоковую работу автоматически параллельной. Для отдельного free-threaded эксперимента нужны совместимые wheels и проверка потокобезопасности. Текущая граница «Session только на вызывающем потоке» сохраняется.

[Frame pointers, PEP 831](https://peps.python.org/pep-0831/) улучшают системное профилирование сборок, которые их используют. Это свойство сборки интерпретатора и native extensions, а не повод менять бизнес-код. Конкретные build flags следует сохранять вместе с результатом benchmark.

## Что считается доказательством для миграции

Нужны одинаковые зависимости и сценарии на обеих версиях, полные тесты, проверки native import, зафиксированные архитектура/сборка/GIL/JIT и независимые повторные замеры wall time, CPU и peak RSS. Сравнение включает текущую фактическую среду и заявленную production-ветку 3.14. Проверки PostgreSQL/Docker/MediaInfo на macOS без этих сервисов не считаются пройденными.

Отсутствие синтаксических ошибок и наличие новых функций недостаточны. Отрицательный либо неубедительный результат оставляет production Python прежним; диагностическая оболочка остаётся необязательной и на старом Python выдаёт понятный отказ.

## Проверка добавленной оболочки

`python -m pytest -q tests/test_runtime_profile.py` из `backend/`: по 18 passed на CPython 3.13.2, 3.14.8 и 3.15.0. На 3.15 также прошёл `compileall` двух новых файлов. Тесты проверяют границы аргументов, отказ старого runtime, совместимость режимов, UTF-8 dump, отсутствие перезаписи при гонке и публикации неполного результата. Они не запускают ALTT, qB, Kensetsu и не читают `.env`.

Реальный `python3.15 -m profiling.sampling attach --help` и `dump --help` на сборке CPython 3.15.0 подтвердили поддерживаемые флаги. Сборка macOS arm64: GIL включён, JIT недоступен/выключен. Затем оболочка запущена на собственном временном asyncio-процессе без приложения и сети: async dump и attach на 1 секунду отказали с `Permission Error: Unable to access process memory on macOS`. Обе команды вернули 1 и не оставили итоговый файл. Повышение прав не выполнялось. Поэтому в этой среде подтверждены CLI-контракт и корректный отказ оболочки, но успешное чтение стеков не заявляется.
