# ТЗ Автоматический кодировщик

Дата: 18 октября 2026. Статус: реализовано в рабочем дереве; результаты проверки приведены в конце.

## 1. Продуктовое решение

Автоматически отправлять в Kensetsu новые и изменённые видеофайлы AVC из отслеживаемых релизов. Один релиз получает собственную комбинацию видео-пресета, аудио-пресета и downmix. Например, для релиза А назначены HEVC + Opus + Stereo, для релиза Б — HEVC + Copy + без downmix. Параметры одного релиза не влияют на другой.

Подтверждено пользователем:

- «Отслеживаемые» — существующий список Telegram: `TrackedRelease.enabled=true`, управляемый `/add` и чекбоксом релиза.
- Для релиза назначается собственный пресет; отдельного списка отслеживания кодировщика нет.
- Обрабатываются **все новые и изменённые AVC**, во всех разрешениях и типах рипа. Выбор одного варианта исходника не вводится.
- Источник актуального контракта Kensetsu — `/Users/geekaz0id/cursor/al-web-video-encoder/docs/API.md`.

Рекомендуемые решения v1, предлагаемые этим ТЗ:

- Общая галочка «Автоматический кодировщик» по умолчанию выключена.
- Без индивидуально назначенных параметров релиз использует «Автоматический» режим: текущие effective defaults Kensetsu для video/audio/downmix. Это уточнение пользователя от 18.10.2026 заменяет первоначальное ожидание назначения.
- Первое включение работает с будущими изменениями. Уже известные версии не превращаются в массовую отправку; для них предусмотрено явное добавление существующих файлов.
- Изменение параметров влияет на ещё не начатые отправки и будущие файлы. Уже принятые файлы автоматически не перекодируются.
- На один точный источник допускается одна автоматическая отправка; ручные отправки участвуют в той же защите повторов.
- При неизвестном результате POST автоматического повторного POST нет. Современный API позволяет восстановить результат чтением квитанции.

## 2. Исходная основа

Ниже зафиксировано состояние ALTT перед реализацией, на котором основано ТЗ. Дальнейшие разделы задают требования новой функции.

- `db/models.py::TrackedRelease` — список Telegram/UI. `jobs/ongoing.py` уже добавляет включённые записи к расписанию, `ongoing_watch` и `ExtraUrl`. При подключении этой функции расширять список целей ongoing не требуется.
- `Release.is_abandoned` — ручная классификация web-интерфейса; она не выключает загрузки/HEVC. В v1 автокодировщик также не использует её как скрытый запрет: для исключения релиза снимается отслеживание.
- `TorrentFile` содержит `(info_hash, relative_path)`, `selected`, `full_path`, sticky `ui_status`, временный `is_checking`, `media_present`. `DiskFileHash` содержит BLAKE3 и gate по размеру/mtime.
- `services/file_tracker.py` и `qb_inventory.py` рано синхронизируют состав. `new` появляется до завершения загрузки и проверки; готовность к отправке из этого не следует.
- `FileTrackerService.track_torrent()` сравнивает полный исходник с prior. `changed` подтверждается расхождением хешей; `ok` — совпадением. Первый торрент без prior остаётся `new` после проверки.
- Prior: сначала предыдущая версия того же `torrent_id`, затем версия того же `release_id` с пересечением exact `relative_path` и подходящей codec/rip family. Basename не является идентичностью.
- `jobs/hash_torrent.py` запускается после `master_complete`; успешный job может содержать частичный/пустой проход. Отсутствие активного job не доказывает, что каждый файл проверен.
- `api/rest.py::_submit_encoder_files` уже выполняет durable claim, проверку текущего архива, пути/media root, `is_checking`, активного hash job, повторную проверку после GET пресетов, exact source identity и size/mtime_ns.
- `encoder_history.py` защищает одинаковый `(сервер, info_hash, relative_path, video_id, audio_id, downmix)` между процессами, хранит квитанцию и не повторяет unknown автоматически. Это защита одной версии с теми же параметрами, а не дедупликация всех содержательно одинаковых переизданий.
- `EncoderSubmission`/`EncoderSubmissionItem` — приём исходника; `EncoderJob`/`encoder_tracking.py` — дальнейшее исполнение и доступность результата. Эти сущности разделены.
- Текущий `video_kensetsu.encode()` отправляет `path`/`paths`, `video_id`, `audio_id`, `audio_downmix`, но **не передаёт Kensetsu локальный request_id**. HTTP 202 пока не является поддерживаемым успешным ответом этого клиента.
- В `base.html` есть общий выбор пресетов, single/batch send и request_id, в `/encoder-history` — журнал, в SSE — обновления квитанций/заданий. Автоматической политики на релиз и постоянной очереди автоотправок нет.

## 3. Условия автоматической обработки

Автоматический POST разрешён только при одновременном выполнении условий:

1. Включены интеграция Kensetsu и общая галочка автокодировщика; задан URL.
2. `TrackedRelease.enabled=true` для release_id.
3. У релиза сохранены и проверены `video_id`, `audio_id`, `audio_downmix`.
4. Архив относится к текущему выбранному источнику, `api_present=true`, `superseded=false`.
5. Codec family архива достоверно AVC. HEVC и AV1 исключаются; неизвестный codec даёт «Ожидает метаданных», без определения по одному basename.
6. Это видеофайл, выбранный на master (`selected=true`); изображения, nfo, вложения и служебный мусор исключаются.
7. Версия файла относится к будущему изменению после активации либо явно включена через добавление существующих файлов.
8. Итоговый sticky `ui_status` — `new` или `changed`; `ok` и `removed` не отправляются автоматически.
9. Есть подтверждение проверки **этого файла этой версии**: BLAKE3 + размер + mtime_ns + время/поколение проверки, полученные завершённым hash-settle или валидным gate-cache.
10. Нет `is_checking` и активного `hash_torrent` в pending/running/stopping для info_hash; исходник доступен как полный обычный файл внутри media root.
11. Нет принятой, отправляющейся или неизвестной ручной/автоматической попытки, запрещающей повтор.

Зелёный health-индикатор — справочная информация, а не доказательство настройки внутреннего источника и не постоянное право на отправку. Недоступный сервер вызывает ожидание/диагностику, не потерю кандидата.

Не ждать `pipeline.done` или полной загрузки slave: исходник готов на master после проверки. Успешная отправка/кодирование не меняет pipeline, sticky ui_status или наличие HEVC-раздачи.

## 4. Новые и изменённые файлы

`new`/`changed` сохраняют существующее значение из `.cursor/rules/sticky-file-status-history.mdc`. Кодировщик читает историю, не записывает в неё «отправлен» или «готов».

Нельзя запускать отправку непосредственно из раннего `added`-события, изменения `TorrentFile.updated_at`, `media_present=true`, перехода `master_complete` или факта завершения job. Они только будят проверку кандидатов.

После hash-settle сохраняется отдельное доказательство готовности по exact `(info_hash, relative_path)` со снимком content hash и stat. Запись доказательства и регистрация/обновление кандидата выполняются транзакционно. Для проверки состава и фиксации changed используются существующие prior-правила, без второго независимого diff.

Периодическая сверка восстанавливает пропущенную постановку из сохранённого доказательства после рестарта или сбоя между этапами. Если доказательства нет, файл ожидает hash job; автоматический sender не читает многогигабайтное видео для повторного хеширования.

При частично успешном хешировании подтверждённые файлы можно обработать после снятия общего active-hash блока; остальные ждут собственной проверки. Одна ошибка соседнего файла не делает готовыми остальные и не блокирует их навсегда.

Файлы первой новой версии релиза после активации являются `new` и могут отправляться после проверки. Первоначальный импорт старой админки не является поводом самопроизвольно отправлять весь архив. `notification_baseline` HEVC не используется как состояние кодировщика: у кодировщика свой baseline.

## 5. Активация и baseline

Для каждого отслеживаемого релиза создаётся запись участия, даже если пресет ещё не назначен. Она отделяет начало наблюдения от момента назначения пресета.

Первое включение общей галочки:

- В короткой транзакции регистрируются включённые tracked-релизы и фиксируется множество уже известных **версий архивов** каждого релиза: exact info_hash, включая версии без загруженного состава.
- Эти версии получают причину `activation_baseline` и по умолчанию не попадают в автоматическую отправку, даже если позже для них появятся строки файлов или завершится загрузка.
- Версии/изменения, обнаруженные после этой границы, регистрируются устойчиво. Отсутствие индивидуального пресета не блокирует отправку: используются действующие настройки Kensetsu по умолчанию после обычной проверки готовности исходника.
- Граница не определяется одним `ui_status`, временем хеширования или временем создания строки TorrentFile. Исходная версия могла быть известна до включения, а состав получить после него.

Добавление tracked-релиза через UI или `/add` после первого включения создаёт такую же границу для этого release_id. Если в момент добавления релиз ещё не имел архивов, первый пришедший архив считается будущей версией.

Фиксация границы и регистрация новых версий сериализуются по release_id в совместимом порядке с `release_lock.py`. Обнаруженный конкурентно архив относится ровно к одной стороне границы; повторная сверка не меняет это решение.

В автоматическом режиме новые/изменённые версии отправляются без ожидания индивидуального назначения. Позднее назначение влияет только на будущие и не начатые отправки, baseline и уже принятые источники не отправляются повторно. Уже superseded-кандидаты отменяются; готовится их актуальный преемник по обычным правилам.

Общее отключение auto — **пауза**: сохраняются границы, кандидаты и история, новые наблюдаемые изменения продолжают регистрироваться; внешний POST запрещён. Повторное включение продолжает актуальную очередь без новой базовой границы. UI заранее показывает накопившееся количество.

Снятие Telegram-отслеживания — **исключение релиза**: новые автоотправки запрещены, не начатые кандидаты отменяются с причиной `untracked`. При новом `/add` создаётся новая граница будущих изменений; изменения периода исключения не становятся неявным backfill. История accepted/unknown сохраняется и продолжает защищать от дублей.

Отключение самой интеграции Kensetsu запрещает новые POST и сетевое восстановление квитанций/опрос выполнения согласно существующему контракту настройки. После включения очередь и опрос возобновляются. Запущенные задания Kensetsu не останавливаются автоматически.

## 6. Пресет релиза

В v1 «пресет релиза» — сохранённая комбинация существующих слоёв Kensetsu:

- `video_id`: точный ID из `GET /api/presets`.
- `audio_id`: точный ID из того же ответа.
- `audio_downmix`: `none` или `stereo`.
- `revision`: локальная версия назначения, optimistic concurrency для двух вкладок.
- Метки/безопасный snapshot выбранных параметров и дата проверки.

`stereo` запрещён с `audio_id=copy` и `none` в UI и на сервере. Для другого аудио-пресета downmix выполняет Kensetsu; ALTT не пытается самостоятельно переделывать аудиодорожки. Значения defaults Kensetsu заполняют открытую форму и используются автоматическим режимом без индивидуального назначения; сохранение индивидуального назначения выполняется явным действием пользователя.

Индивидуальный пресет проверяется при назначении и перед POST. Удалённый/недоступный пресет блокирует отправку с объяснением; переход на другой preset или defaults без снятия назначения запрещён. Если изменились доступные через API параметры под тем же ID, отправка ожидает повторного сохранения индивидуального назначения. В автоматическом режиме перед каждой новой отправкой читается `GET /api/presets.defaults`, проверяются IDs, доступность аудио и downmix, а фактические параметры и snapshot фиксируются в квитанции. Пустое назначение при этом не перезаписывается конкретными IDs. Отсутствующие или некорректные defaults не заменяются первым пресетом из списка. Snapshot хранит только наблюдавшиеся поля API и служит аудиту; GET пресетов и POST по их ID не атомарны, поэтому он не гарантирует неизменность конфигурации Kensetsu между этими запросами.

Изменение назначения обновляет параметры не начатых кандидатов после проверки revision. Начатые POST и принятые задания сохраняют прежний snapshot. Проверка revision выполняется повторно после асинхронного preflight; устаревшая подготовка завершается как заведомо не отправленная и ставится заново с новыми параметрами.

Снятие назначения сохраняет участие/кандидатов и возвращает режим «Автоматический». Это не разрешение повторить старые accepted с другим пресетом. Преднамеренное перекодирование принятых источников выполняется существующим ручным сценарием с подтверждением.

Отдельная локальная библиотека именованных профилей, правила «по сезону», автоопределение downmix, индивидуальные настройки эпизодов и произвольные FFmpeg-параметры вне v1. Можно переиспользовать выбор комбинации из другого релиза без создания отдельной сущности профиля.

## 7. Устойчивая очередь и данные

Предлагаемые сущности; названия уточняются при реализации, назначение и гарантии обязательны:

1. `release_encoder_policies`: PK release_id, nullable video/audio IDs, downmix, revision, preset snapshot/fingerprint, проверка назначения, текущая activation generation и времена UTC. Наличие policy не заменяет `TrackedRelease.enabled`.
2. `encoder_auto_sources`: участие exact версии `(release_id, generation, info_hash)`; baseline/будущая версия, первое обнаружение, архивный контекст. Нужна в том числе для версии без состава при активации.
3. `encoder_file_readiness`: immutable либо версионируемое доказательство hash-settle по `(info_hash, relative_path)`: hash/algorithm/size/stat/time/job_id, итоговый sticky status, prior identity. Не заменяет DiskFileHash и историю FileChangeEvent.
4. `encoder_auto_items`: exact identity, ссылка на readiness, причина `new|changed|explicit_backfill`, generation/revision, состояние, reason code, next_attempt_at, attempt count, lease/token, связь с submission/item и безопасный snapshot решения.
5. Дополнения истории: origin `manual|auto`, policy revision/auto item, неизменяемый удалённый payload и request_id, сведения восстановления квитанции. Исходный диагностический ответ POST сохраняется отдельно от поздней read-only квитанции.

Для auto items обязательны уникальность logical candidate и индекс срока/lease; все внешние действия используют общий ledger истории. Удаление/пересоздание TorrentFile не создаёт нового права отправки. Квитанции, content identity и unresolved-попытки переживают supersede и операционные сбросы.

Минимальные состояния auto item: `waiting`, `ready`, `claimed`, `receipt_pending`, `accepted`, `needs_attention`, `cancelled`. Состояние waiting имеет одну актуальную причину: preset (неполное индивидуальное назначение), settings (изменение параметров до следующей сверки), metadata, hash, download, server, global pause. Приём/выполнение Kensetsu остаются отдельными существующими состояниями.

Требуется Alembic-миграция. Старые данные не порождают автоотправки при миграции, общая галочка остаётся выключенной. Существующая история учитывается при первом включении.

## 8. Дедупликация и конкуренция

Вынести общий application service отправки из REST-обработчика. REST и worker вызывают его напрямую; worker не вызывает собственный HTTP API и не импортирует бизнес-процесс из `main.py`. Сохраняются существующие проверки и `encoder_history.claim`.

Существующий exact-source claim расширяется общей координацией ручного и автоматического начала. Для auto дополнительное правило: `sending`, `accepted` или `unknown` по тому же exact источнику блокируют auto **независимо от пресета и текущего URL**. Обычная ручная отправка тоже проверяет такие автоматические попытки по exact/content identity независимо от параметров: если первой началась auto, смена пресета или URL в ручной форме не обходит её claim. Эти проверки выполняются в общем сервисе под общими locks; одних одинаковых locks без проверки конфликта недостаточно. Смена назначения/сервера не является автоматическим разрешением повторить исходник. Исключение для accepted/unknown доступно только через существующий явно подтверждённый ручной повтор; активный `sending` не обходится даже подтверждением.

Дополнительная защита переизданий использует подтверждённую content identity `(release_id, exact relative_path, hash_algo, content_hash, size)`: одинаковые байты того же пути под другим info_hash повторно автоматически не кодируются. Новый exact relative_path остаётся новым файлом и получает собственного кандидата, даже если байты совпадают с файлом другого пути. Разные разрешения/рипы AVC обрабатываются все; сопоставление по basename и дедупликация между разными release_id запрещены. Эта защита управляет только отправкой и не меняет sticky-историю.

Content identity фиксируется при каждом новом ручном и автоматическом claim, когда есть актуальное доказательство. Конкурирующие manual/auto используют одинаковые advisory locks и порядок взятия exact/content locks. Проверки конфликтов выполняются повторно под locks. Нельзя сначала выполнить два POST и затем дедуплицировать журнал.

У старой квитанции может не быть достоверного content hash: не вычислять его по сегодняшнему изменившемуся пути. Exact accepted/unknown по-прежнему блокирует; доказанную content identity переносить из сохранённого snapshot. Для переиздания того же пути с незакрытым старым unknown без content evidence требуется ручной разбор: автомат не делает вывод, что старое задание относится к другим байтам.

Новые байты того же relative_path после подтверждённой пересборки образуют нового кандидата. Если старая unknown имеет доказанный другой hash, она не блокирует обработку новых байтов; если доказательства недостаточно — показывается конфликт источника, а не выполняется догадка.

Ручная отправка, принятая первой, снимает соответствующий auto item с отправки с причиной `already_submitted` и ссылкой на квитанцию. Если первой победила auto, ручной интерфейс получает штатный конфликт истории. `unknown` никогда не обходится автоматически флагами allow_repeat/acknowledge_unknown.

## 9. Отправитель и перезапуск

Worker каждые 30 секунд выполняет ограниченную сверку и отправку; hash-settle может дополнительно будить обработку. Рекомендуемый v1: один исходник на HTTP POST, один параллельный POST на сервер. Это ограничивает копирование на Unraid и упрощает восстановление; все пригодные AVC последовательно попадут в Kensetsu. Параллелизм самого кодирования остаётся настройкой Kensetsu.

Claim очереди — атомарный с lease/token и fencing; второй worker не получает того же владельца. Актуальные настройки, tracked, archive, readiness, revision и stat перепроверяются в той же короткой транзакции, которая фиксирует `request_started_at`, с общей координацией изменений разрешающих настроек и tracked/policy. Durable `request_started_at` — граница начала отправки для паузы, untrack и смены пресета: после неё попытка считается начатой и может выполнить HTTP со старым snapshot, даже если сеть ещё не вызвана. Отключение запрещает новые intent, но не отменяет уже начатые; это ограничение показывается в UI. Lease больше предельного POST либо продлевается; просроченный claim не разрешает повтор побочного действия.

Фиксируются submission, frozen JSON payload, stable request_id и source snapshot до HTTP. Никакая SQL-транзакция, блокировка строки или занятое соединение не удерживается на время сетевого запроса. Отложенный ответ применяется только к соответствующей попытке; старый token не меняет новое состояние очереди.

Kensetsu копирует исходник во время POST; его API не возвращает доказательство BLAKE3 скопированных байтов. После ответа повторно проверяются доступные stat/identity: обнаруженное изменение фиксируется отдельно как `source_conflict`/needs_attention, исходная квитанция и job IDs сохраняются, автоматического нового POST нет. Даже неизменный stat не даёт абсолютной гарантии неизменности байтов во время копирования. Полную атомарность исходника без immutable snapshot текущий контракт не обеспечивает; создание локальных копий всех медиа в ALTT вне v1.

Рестарт до durable фиксации `request_started_at` даёт доказанно неотправленную попытку и безопасное повторное планирование. После этой фиксации отсутствие квитанции означает неизвестный исход, в том числе при падении до фактического вызова HTTP. Lease не доказывает отсутствие внешнего эффекта.

Автоматически повторяются только доказанно не начатая отправка и временная недоступность при подготовке/соединении до передачи запроса: в текущей классификации это ConnectError/ConnectTimeout/PoolTimeout. ReadTimeout, WriteTimeout и потеря ответа после передачи оставляют неизвестный исход и разрешают только чтение квитанции. Рекомендуемый backoff: 30 с, 60 с, 120 с, затем до 15 мин с jitter; на уровне сервера общий cooldown, чтобы релизы не создавали шторм. Положительный HTTP-отказ не ретраится бесконечно: preset/path/403 → требуется действие. Для rejected разрешается отдельный контролируемый повтор после исправления причины, с новым request_id и ссылкой retry_of; accepted/unknown не входят в этот путь.

Очередь сверяет актуальность: superseded/api-absent/untracked и подтверждённое исключение exact файла из текущего состава отменяют не начатого кандидата с причиной. Само отсутствие файла на диске, ошибка доступа к mount или незавершённая загрузка оставляют ожидание; они не доказывают удаление из состава. Старое поколение не подменяется текущим исходником внутри прежней попытки.

Отсутствие worker отображается как задержка очереди. Открытый браузер, SSE-подписчик и процесс Telegram-бота не являются условиями автоматизации.

## 10. Контракт Kensetsu и неизвестный результат

В актуальном локальном контракте и реализации Kensetsu уже есть:

- `GET /api/presets`; `POST /api/internal/encode` с точными `path|paths`, video/audio IDs и downmix.
- Необязательный `request_id` с durable reservation до копирования; готовый replay возвращает исходные job IDs без нового копирования/создания.
- `GET /api/internal/encode/requests/<request_id>` — только чтение квитанции.
- `input_path` каждого job точно повторяет входную строку; успешный ответ/partial сопоставляются по полному пути, не basename и не порядку jobs.
- Готовая квитанция отдаёт исходный HTTP 200/207 или сохранённый код ошибки. HTTP 202 `processing` имеет Retry-After:2; `interrupted` — HTTP 202 без Retry-After с известными, возможно неполными job_ids.
- Другой payload с тем же ID даёт 409. Fingerprint учитывает формат JSON/form, точные поля, отсутствующие значения, алиасы и **порядок paths**. Поэтому payload сохраняется до POST и воспроизводится побайтно эквивалентным по контракту, без нового resolve defaults.

ALTT должен передавать свой сохранённый request_id Kensetsu и поддерживать HTTP 202 как незавершённый приём, без объявления всего запроса принятым. Для v1 автоматическое восстановление использует **GET квитанции**, повторный POST после неизвестного исхода не требуется.

После таймаута/обрыва/рестарта ALTT читает квитанцию на **сохранённом сервере** с тем же ID. Ready подтверждает только сопоставленные исходники; противоречивый input_path не принимается. `processing` опрашивается с Retry-After/backoff. `interrupted` требует внимания; известные job_ids можно читать и сопоставлять по input_path, но это не доказательство полноты запроса.

404 квитанции не является доказательством, что задания не создавались: это может быть legacy, потеря SQLite или неверная версия сервера. Legacy без request receipts, 403, interrupted, неизвестный/противоречивый ответ сохраняют неизвестность и запрещают автоматический новый POST. Для legacy повтор возможен только существующим явным ручным действием после проверки Kensetsu.

Повторный GET и поздняя доказанная квитанция могут перевести unknown в accepted с сохранением исходного transport outcome и audit recovery. Готовая квитанция не используется как текущий прогресс: после accepted работает существующий encoder_tracking GET job/HEAD legacy.

Перед включением проверяется контракт установленного Kensetsu и общий mount исходников. Нового endpoint обнаружения возможностей это ТЗ не требует; его в контракте нет. Проверка локального исходного кода не подтверждает версию развёрнутого сервера.

## 12. Уже существующие файлы

Предусмотреть отдельное действие «Добавить существующие файлы» у релиза. По умолчанию ничего не выбрано. Предварительный просмотр показывает только актуальные выбранные AVC-видеофайлы со sticky new/changed, их готовность, параметры и причины исключения/дедупликации.

Это не отменяет проверку hash/stat/актуальности непосредственно перед отправкой, не снимает unknown/accepted guard и не включает HEVC. Старые `ok` не входят в этот сценарий; для произвольного кодирования остаётся ручная отправка.

Предпросмотр не выполняет внешнего POST, полный каталог не сканируется по диску без ограничения страницы/пакета.

## 14. Критерии приёмки

1. Два tracked-релиза с разными комбинациями получают свои параметры; downmix одного не распространяется на другой. Без индивидуального пресета новые POST используют текущие defaults Kensetsu; недоступные defaults не приводят к отправке с выдуманными параметрами.
2. Все разные AVC-варианты 720/1080/WEBRip/WEB-DL обрабатываются; HEVC/AV1 исключены; unknown codec ждёт метаданных. Успех кодирования не меняет pairing и sticky.
3. Первый новый торрент после активации отправляет все проверенные new-видео. До master completion/hash-settle, при checking, active hash или stale stat отправок нет.
4. Дополнение батча: старые `ok` не отправляются, новый episode `new` отправляется один раз. Пересборка exact path с prior hash mismatch отправляет changed один раз; unchanged hash не отправляется.
5. Sticky статусы до/после принятых/ошибочных заданий одинаковы. Снятие временного overlay не превращает baseline/new в разрешение отправки.
6. Первое включение с сотнями существующих sticky new/changed не создаёт POST. Состав baseline-архива, загруженный позднее, также не отправляется без явного выбора.
7. Файл, обнаруженный после активации во время хеширования, переживает рестарт и ожидание пресета; после готовности получает одну отправку. Гонка регистрации с baseline однозначна.
8. Смена пресета при ожидании применяет новую revision; при POST сохраняется старый snapshot; accepted не отправляется заново. Удалённый/изменившийся индивидуальный preset блокирует, переход к defaults требует явного снятия назначения. Автоматический режим берёт актуальные defaults для каждой новой отправки; восстановление неизвестного приёма их не читает заново.
9. Manual/auto и два worker конкурируют: один внешний POST для одного источника, включая переиздание тех же байтов с новым info_hash при том же exact relative_path. Разные пути и другие AVC-варианты того же эпизода не схлопываются. При неизвестном результате действует запрет нового POST, а не обещание гарантированного приёма каждого исходника.
10. Старый accepted/unknown не обходится новым пресетом или URL. Пересоздание TorrentFile не снимает guard. Неоднозначная legacy content identity требует разбора.
11. Падение до durable фиксации `request_started_at` допускает безопасное планирование; после неё падение/timeout даёт unknown/receipt_pending, даже если фактический HTTP ещё не начался. Lease, рестарт и повторный tick не создают второй POST.
12. Modern request_id передан; frozen payload стабилен. GET ready восстанавливает accepted; processing учитывает Retry-After; interrupted/404/legacy/противоречие не повторяют POST. ID/payload conflict 409 видим отдельно.
13. Receipt/status/error сопоставляются по exact input_path; одинаковые basenames и изменённый порядок batch не дают ложного accepted. HTTP 202/207 и неполная квитанция не принимают всю пачку по догадке.
14. Global pause и Kensetsu off запрещают новые POST, сохраняют очередь; resume обрабатывает только актуальные backlog-файлы. Tracking off отменяет не начатые; повторное добавление работает от новой future-only границы.
15. Исторические source/pipeline/media статусы не подменяются друг другом; superseded отменяется, временно недоступный диск ждёт. `is_abandoned` и HEVC ignore не становятся скрытыми правилами auto.
16. Предпросмотр backfill не пишет в Kensetsu; отправляет только явно выбранные доступные exact версии и не обходит duplicate guard.
17. SSE сохраняет редактируемую форму/selection/scroll/focus; два сохранения с одной revision дают один успех и понятный конфликт. Счётчики различают приём, выполнение, доступность и связь.
18. Alembic upgrade/downgrade/re-upgrade и начальная выключенная настройка проверены на отдельном PostgreSQL 16. Реальные конкурирующие Session проверяют locks/claim/recovery; SQLite mock недостаточен для этих гарантий.
19. Изменение исходника во время POST даёт отдельный source_conflict с сохранёнными квитанцией/job IDs; оно не становится ни подтверждением точного content hash Kensetsu, ни разрешением автоматического повтора.

## 18. Автоматический пресет и настройка в релизах — 18.10.2026

По уточнению пользователя отсутствие обоих ID назначения означает текущие defaults Kensetsu. Перед новой отправкой они проверяются по каталогу, затем конкретные ID, downmix и snapshot записываются в квитанцию. Policy остаётся пустой, поэтому следующий новый файл получает уже актуальные defaults. Неизвестные, недоступные и некорректные defaults не приводят к POST; неполная индивидуальная пара не превращается в автоматический режим. Для назначенного пресета сохраняется проверка snapshot, для обоих режимов — revision, lease и source guards. Потерянный ответ восстанавливается только через GET старой квитанции, без повторного чтения defaults и POST.

В карточке `/releases` показываются состояние автокодирования и автоматический режим либо сохранённые названия видео/аудио с downmix. Назначение и возврат к автоматическому режиму доступны прямо в карточке. После PUT обновляются подтверждённые параметры и revision; запоздалый SSE не откатывает их. Диалог защищён от swap, а раскрытия и положение страницы сохраняются общим механизмом UI. Policy читаются одним запросом для ID текущей страницы; состояния настроек учитываются в change token релизов. Дополнительная миграция для этого уточнения не нужна.

Проверки: **1562 passed, 1 optional MiniJinja skip** на обычном CPython 3.15.0 с отдельной PostgreSQL 16; четыре JS-набора и compileall. Runtime, миграция и девять HTTP-запросов проверены в точном собранном образе на ARM64 и AMD64 (последний под эмуляцией). В браузере на изолированных данных проверены сохранение Copy со сбросом stereo, возврат к automatic, повторное назначение Opus + Stereo и сохранение раскрытой карточки при SSE; сеть Kensetsu подменена, настоящее кодирование не запускалось. Публикация и digest фиксируются в отдельном отчёте релиза.
