# Рабочий список HEVC

Статус: проект проверен, отдельные service/router/templates/client реализованы, 2026-10-13; общая интеграция и итоговая проверка выполняются root. Страница — представление существующих данных и ручных действий. Она не создаёт очередь исполнения, не отслеживает прогресс кодирования и не меняет правила AVC/HEVC, sticky-статусы или историю отправок.

## Задача

Пользователь на одном экране видит, почему нужен HEVC, какой конкретно исходник доступен для отправки, что Kensetsu подтвердил при последней отправке и какое действие безопасно выполнить. Не нужно раскрывать каждый релиз и отдельно искать квитанцию.

Предлагаемые маршруты: `GET /hevc-workbench` и `GET /hevc-workbench/live`. В навигации — «Рабочий список HEVC» рядом с «Релизы» и «Отправки в Kensetsu».

## Единица отображения

Одна строка — точная версия видеофайла: `(info_hash, exact relative_path)` из `TorrentFile`, с `file_id` для существующего API и `archive_id` для навигации. Одинаковый basename в разных каталогах или новый hash не объединяются. Если активные архивные записи содержат один hash, источник показывается один раз с детерминированно выбранной новейшей активной записью. Условие активности соответствует текущему download/send API: `api_present=True`, `superseded=False`.

Основной набор — активные AVC-архивы, возвращённые `find_unpaired_avc`: `missing`, `overdue`, `type_mismatch`. Состав видео определяется существующим списком видео-расширений/классификацией, junk и `.!qB` не являются кандидатами для кодирования. Исторические AVC обязательно остаются во входе pairing для SLA-якоря, но не становятся отправляемыми строками.

Чтобы не терять неоднозначный приём после появления HEVC, представление «Приём требует проверки» дополнительно включает точные **активные AVC-источники** с последней квитанцией `unknown`, даже если текущий pairing уже закрыт. Для такого источника выводится «Проблема HEVC больше не обнаружена», а не выдуманная ошибка pairing. Историю удалённых/заменённых источников пользователь открывает в существующем журнале отправок.

Если у проблемного архива нет известных видеофайлов, показывается отдельная невыбираемая строка «Состав видеофайлов ещё не получен» с архивом/hash. Это диагностический кандидат архива, а не фиктивный `file_id`. Если известны только невыбранные видеофайлы, они видны с конкретной причиной блокировки.

## Строка и независимые состояния

Строка содержит пять областей:

1. Выбор и релиз: чекбокс только у разрешённых источников, название, точный relative_path, размер, торрент/архив. Ссылки на текущий релиз, архив и pipeline; публичная ссылка только для site, backoffice получает ссылку админки.
2. Потребность HEVC: «HEVC отсутствует», «HEVC отстаёт» либо «Расхождение типов» из `UnpairedAvc.status`; распознанный тип/качество/эпизоды. Возраст от существующего SLA-якоря, источник часов API/локальный, при `overdue` отдельно «Сверх SLA: N ч». Pure missing после 24 часов не переименовывается в overdue. `type_mismatch` не попадает в представление просроченных.
3. Исходник: после ограниченной проверки видимых строк «Файл доступен · проверено HH:MM:SS» либо все известные причины блокировки. Отдельно подписывается, что progress qB и активное хеширование взяты из последнего DB-снимка. Путь, `media_present`, `selected`, `is_checking`, активное хеширование и sticky-история показываются раздельно. `new`/`changed` не мешают отправке полного файла и не превращаются в `ok`. Файловая проверка не меняет сохранённые media/sticky-флаги.
4. Kensetsu: последняя квитанция точного `(info_hash, relative_path)` с формулировками из `encoder_history.LABELS`; отсутствие квитанции — «Отправок этой версии нет». По клику открывается соответствующая отправка. Это состояние приёма, не состояние кодирования. Более новая версия файла не наследует квитанцию старого hash.
5. Действие: обычная отправка доступного нового/неотправленного/отклонённого источника; у `sending`, `accepted`, `unknown` — переход к журналу. Повтор уже принятого/неизвестного приёма остаётся в текущем явном сценарии журнала с подтверждением риска. Никаких автоматических `allow_repeat`/`acknowledge_unknown`.

Подробности строки раскрываются через `<details data-sse-key="hevc-file-<file_id>-<info_hash>">`: полный exact путь, hash, sticky-статус, pipeline, парный HEVC/архив, время-якорь и последняя квитанция. Новый экран не требует on-demand MediaInfo, чтения MKV или BLAKE3.

## Представления, поиск и пагинация

Параметр `view`: `all` (по умолчанию), `ready`, `overdue`, `unavailable`, `unknown`. Вкладки могут пересекаться: просроченный источник одновременно бывает недоступным. Счётчики отражают файлы/диагностические строки, не релизы. Счётчики «кандидатов готовности»/«недоступных» явно подписаны «по данным последней проверки»: весь каталог не сканируется по диску. Для видимой страницы отдельно указано точное число проверенных доступных/недоступных файлов и время проверки.

- «Все»: текущие проблемы HEVC и активные источники с неоднозначным приёмом.
- «Готово к отправке»: сначала отбирается страница предварительных кандидатов по БД (есть проблема HEVC, отсутствуют известные блокировки, последняя квитанция не `sending`/`accepted`/`unknown`), затем проверяются пути только этой страницы. В основном списке остаются подтверждённые доступные файлы. Кандидаты, чей файл исчез/стал неполным/оказался вне root, выводятся отдельным невыбираемым блоком «Доступность изменилась при проверке» с причиной; они не маскируются как готовые. Пагинация относится к предварительным кандидатам, что явно указано рядом с total/page. Не заполняем страницу бесконечным перебором всего диска. Перед реальной отправкой endpoint всё равно проверяет заново.
- «Просрочено»: только `status == overdue`; смысл и SLA совпадают с существующими фильтрами.
- «Исходник недоступен»: не получен состав, не выбран файл, отсутствует путь/медиа по БД, sticky removed/неизвестный, идёт проверка/хеширование, служебный/неподдерживаемый источник. Причина не маскируется одной общей надписью. Представление явно подписано «Недоступные по данным последней проверки» и не утверждает полноту обнаружения пропавших файлов во всём каталоге. Видимые строки перепроверяются по диску: появившийся файл отмечается как изменение доступности, но DB-данные не перезаписываются. Новое исчезновение файла в других представлениях показывается сразу в текущем списке/блоке изменений, даже если прежний DB-фильтр его не отбирал.
- «Приём требует проверки»: последняя квитанция `unknown`; нет прямой кнопки повторной отправки.

Поиск по названию/alias релиза, числовому release_id/torrent_id и exact relative_path. Размер строки ограничивается/нормализуется сервером, SQL использует bind-параметры. Выбор представления и поисковая строка сохраняются в URL. Первая версия — 30 строк на страницу, максимум 100; page нормализуется и зажимается до последней доступной страницы.

Порядок фиксирован: `overdue`, `missing`, `type_mismatch`, только квитанция; внутри — более ранний SLA-якорь первым, затем release_id, archive_id, relative_path, file_id. Последние поля обеспечивают устойчивую пагинацию. Это новое представление; существующий порядок `/releases` не меняется.

## Готовность и ограничения отправки

Чтение страницы не вызывает qB/Kensetsu и не записывает media/sticky-флаги. Предварительное разрешение выбора строится по сохранённым флагам и `file_status_for_ui` с активным hash job. Затем **только для текущих 30, максимум 100 строк** проверяется complete-файл и разрешение symlink/root с текущими download guards: обычный файл под media root, не сам `.!qB`; соседний `.!qB` при существующем complete не блокирует. Проверка группирует пути по parent и использует один scandir на уникальный parent; canonical/root guards сохраняются, ошибка доступа становится понятной причиной блокировки. Нет повторного чтения файлов для всех архивов, нет MKV parsing/hash. Неизвестная/ошибочная FS-проверка закрывает выбор.

Кнопка «Проверить доступность страницы» обновляет этот же ограниченный набор. По SSE срабатывает та же bounded-проверка видимых строк; частота ограничена существующим интервалом refresh (не чаще одного refresh на target за 3 с), а минутный tick обновляет возраст/актуальность. Дисковые изменения между проверкой и кликом остаются возможны, поэтому время проверки всегда видно и send endpoint остаётся источником финального решения.

Весь batch идёт через **существующий** `POST /api/torrent-files/send-to-encoder`; текущий лимит — `ENCODE_BATCH_MAX_FILES=100`. Пресеты выбираются существующим `pickEncoderPreset`, запрос отправляется через `submitEncoderFiles` с существующим request_id/replay/claim. Экран не создаёт альтернативный endpoint побочного эффекта и не ослабляет duplicate guard. Последняя квитанция не является полной историей по всем пресетам: более старый accepted/unknown может по-прежнему вызвать 409. Такой конфликт отображается с переходом в журнал, без обхода защиты.

Текущий endpoint заново проверяет актуальность архива, разрешённый sticky-статус, границу media root, complete-файл, exact hash/path и size+mtime_ns после асинхронной загрузки пресетов. Он не выполняет новый qB-запрос и не блокирует отдельной проверкой `selected`/`is_checking`/активный hash job. Поэтому эти флаги консервативно блокируют выбор в новом UI; если требуются такие же гарантии при гонке с отправкой, общую проверку endpoint надо усилить в shared `rest.py`, а не приписывать её существующему коду.

При частичном приёме снимается выбор только с подтверждённых `file_ids`. Ошибки и неоднозначные результаты остаются видимыми; следующий обычный batch не получает разрешение повторять их молча. При потере ответа повтор того же request_id возвращает текущую квитанцию вместо второго POST Kensetsu.

Первая версия поддерживает выбор **на текущей странице**. При явном переходе к другой странице/поиску выбор сбрасывается; рядом с кнопкой «Выбрать доступные на странице» это указано. Скрытая межстраничная отправка не появляется. Лимит 100 проверяется и в UI, и существующим API.

## Данные и производительность

Выделенный `services/hevc_workbench.py` строит context без изменения моделей/миграций. Он не вызывает `list_release_groups`: иначе повторит pairing и работу неиспользуемых сводок/файлов.

1. Один bulk SELECT компактных архивных полей, включая исторические, с фиксированным `now=utcnow()` на весь запрос.
2. Один bulk SELECT `(info_hash, relative_path)` всех нужных составов для `file_keys_by_archive_id`; для ограничений параметров можно чанковать IN по 500 hash. Один вызов `find_unpaired_avc` на весь набор, без per-release повторного вычисления.
3. Bulk SELECT компактных полей активных видеофайлов нужных AVC и источников с `unknown`, плюс bulk запрос активных hash jobs. Для фильтров готовности/счётчиков нужны DB-снимки кандидатов до пагинации; это O(каталог), но без N+1 SQL/FS, ORM relationships и содержимого медиа. Весь каталог **не** проверяется повторно по диску.
4. Последнюю квитанцию получать один раз SQL-проекцией/оконной функцией `row_number() over(partition by info_hash, relative_path order by id desc)` с join необходимых полей submission. В фильтр unknown попадает именно последняя квитанция; старый unknown, закрытый новой accepted, не считается актуальным. Не запускать `latest_receipts` отдельно для каждой строки: текущий helper читает все item по hash и вызывает recovery. Сервис списка остаётся read-only. Для просроченного `sending` можно вывести effective-status по **той же** семантике recovery: `unknown`, если request_started_at есть, иначе `not_sent`; подписать «Отправка прервана, состояние будет сохранено при обращении к журналу». Это не доказательство приёма и не разрешение повтора неизвестного результата. Фактическое recovery выполняет существующий API журнала/отправки.
5. Фильтрация/сортировка компактных DTO и пагинация в памяти. Полные подробности, метаданные релизов и ссылки загружаются bulk только для текущей страницы. Счётчики считаются из того же DTO-снимка и выбранного поиска. Только после выбора страницы выполняется ограниченная FS-проверка её кандидатов; проверенное число и время отделяются от предварительных DB-счётчиков.

Отдельный индекс/материализация не вводятся без замера. На тестовом корпусе из операции HEVC (1024 релиза, 5248 архивов, 43392 файла) проверяется один pairing на запрос, отсутствие N+1, файловая активность только для страницы/уникальных parent и нулевая сетевая активность. Фиксируется wall time целого service/HTML запроса; CPU/RAM вторичны. Это проверка масштаба, не обещание тех же миллисекунд на Unraid.

## SSE и состояние UI

Новый канал `hevc_workbench` собирает изменения архива/файлов/релизов, активных hash jobs и отправок. Нужен минутный tick для изменения SLA и истечения отправки даже без записи БД. Сам канал использует дешёвые token-проекции и не запускает pairing; контекст HTML вычисляется только при refresh. Настройки включения/URL кодировщика тоже должны менять token/глобальную доступность действия.

Корень partial — стабильный `#hevc-workbench-live` с текущим URL фильтра/page и `data-ui-sse-channel="hevc_workbench"`. SSE обновляет строки и счётчики, не форму фильтров и не диалог пресетов. Во время отправки partial не должен уничтожать результат/фокус диалога; отправка и её request_id живут в общем JS.

Текущий `captureUiSsePreserve` сохраняет выбранные file_ids только внутри `details.torrent-files`. Для таблицы нужна явная поддержка выбранных `.file-encode-check` со стабильным `(file_id, info_hash, relative_path)` на корне списка. После swap выбор восстанавливается только если **та же версия** всё ещё видима и разрешена; ставший недоступным/accepted/unknown источник снимается с понятным уведомлением. Нельзя восстанавливать выбор только по basename или копировать старый HTML строки поверх новых данных.

Раскрытые `data-sse-key`, `scrollY`, активное поле/позиция курсора при необходимости сохраняются; lazy-HTML старых torrent files на этой странице не используется. Общая нижняя batch-панель продолжает обслуживать те же `.file-encode-check`; после swap вызывается обновление счётчика. Поле поиска остаётся вне partial. Динамические строки с пользовательскими данными создаются Jinja autoescape/textContent, не `innerHTML` с путями/названиями.

## Владение реализацией

После проверки проекта отдельный агент может менять только новые файлы: `services/hevc_workbench.py`, `api/hevc_workbench.py` (router), `templates/hevc_workbench.html`, `templates/partials/hevc_workbench_live.html`, при необходимости `static/hevc_workbench.js`, `tests/test_hevc_workbench.py`, `tests/test_hevc_workbench_ui.py`.

Root интегрирует router в `main.py`, навигацию/общий JS/hooks в `base.html`, channel/token в `ui_events.py`, и при необходимости общую финальную eligibility-проверку в `rest.py`. Модели, миграции, pairing, sticky и логика claims остаются прежними. Router получает общий templates/зависимости через явный factory, чтобы не импортировать `main.py` циклически.

## Критерии проверки до принятия

- Изолированные SQLite/SQLAlchemy данные (существующий SQLite JSONB compiler из тестов) покрывают missing/overdue/type_mismatch, grace, API/local SLA, historical anchor, ignored/superseded/API-absent, source site/backoffice и ручной abandoned без влияния на pairing.
- Разные hash/relative_path с одним basename не наследуют квитанцию/выбор. Пересозданный file_id той же exact версии получает корректную квитанцию. Нет файлов — видимая диагностическая строка.
- Все причины недоступности; `new`/`changed` доступны при полном исходнике; `checking`/hash-active временно блокируют, sticky не меняется. Граница media root и неполные файлы окончательно проверяются send endpoint.
- Представления, поиск, лимиты/page clamp и стабильный порядок; latest unknown только от последней квитанции, сохраняется после закрытия HEVC-проблемы для активного AVC.
- accepted/sending/unknown не выбираются обычным batch; partial outcome снимает только accepted; 409 ведёт к истории; никаких повторов/флагов обхода автоматически. Существующие `test_encoder_history*` остаются зелёными.
- Pairing вызван один раз; DB операции bulk; qB/MediaInfo/Kensetsu замоканы fail-fast при GET страницы. FS probe получает не более 100 видимых кандидатов, проверены symlink escape/partial-only/complete+partial/permission error и отсутствие скана невидимых файлов. Количество SQL не растёт линейно от числа строк; общие readiness-счётчики и пагинация честно отражают предварительный DB-отбор.
- HTML/JS проверки сохранения selection/details/scroll после SSE, удаления только ставшего неeligible выбора, сохранения preset dialog/request_id, escaping названий/путей. Реальный browser smoke проводится с изолированными данными без отправки в живой Kensetsu.
- Регрессии `test_hevc*`, `test_releases_view*`, `test_encoder_history*`, `test_ui_events.py`, затем полный suite обычного CPython 3.15 из `backend/`.

## Проверка проекта по существующему коду
