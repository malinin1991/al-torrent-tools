# ТЗ: однозначные квитанции Video Kensetsu для AL Torrent Tools

Обновление 14 октября: новый контракт Kensetsu уже описан в
`/Users/geekaz0id/cursor/al-web-video-encoder/docs/API.md`. Он реализует input_path,
output_available/download_url/output_size_bytes и внешнюю идемпотентность.
Пункты ниже сохраняют контекст первоначального ТЗ. ALTT использует новые поля
готовности и точного исходника, с HEAD fallback для legacy-версии API.

## Наблюдение 14 октября 2026

AL Torrent Tools отправил один исходник в `POST /api/internal/encode` и получил
HTTP 200: `created: true`, `queued: true`, `encoding_started: false`,
`job.status: planned`, `job.id: 2ce50252-10ed-4382-839b-5a3e96b3df16`.
Поле `job.filename` содержало `Hotaru_no_Yomeiri_[01] .mkv`, без полного пути.
ALTT ошибочно сравнил его с полным путём и записал «Приём не подтверждён».

Это подтверждение создания задания в очереди. Готовность результата сообщается
уже существующим `GET /api/jobs/<job_id>`, а не первоначальным POST.

При проверке этого задания GET вернул `done`, `progress: 100.0`,
`completed_at: 2026-10-14T05:06:23.365985Z`. HEAD существующего
`/api/jobs/<job_id>/download` вернул HTTP 200, `video/matroska` и
`Content-Length: 238014293`. Файл готов и доступен; повторная отправка не нужна.

## Обязательное изменение для надёжного batch: исходный путь

В объекте каждого успешно созданного задания из `/api/internal/encode` добавить
строковое поле `input_path`, **точно равное входному `path` / элементу `paths`**.
Оно необходимо и для single, и для batch. Сохранять его в данных задания и
возвращать также через `GET /api/jobs/<job_id>`.

Не использовать для этого `Job.original_path`: внутренний endpoint копирует
исходник в uploads, и original_path задания указывает на эту временную копию.
Имя файла и позиция в массиве не определяют исходник: разные каталоги могут
содержать одинаковый basename, а пакет может завершиться частично.

Существующие `errors[].path` сохраняют исходный путь аналогичным образом.
Статусы HTTP 200/207, single-envelope `job` и batch-envelope `jobs` сохранить.
Это добавление полей, совместимое с существующими клиентами.

Пример квитанции одного файла:

```json
{
  "created": true,
  "queued": true,
  "encoding_started": false,
  "job": {
    "id": "2ce50252-10ed-4382-839b-5a3e96b3df16",
    "input_path": "/anilibria/2026/Hotaru no Yomeiri - AniLiberty [WEB-DL 1080p]/Hotaru_no_Yomeiri_[01] .mkv",
    "filename": "Hotaru_no_Yomeiri_[01] .mkv",
    "status": "planned",
    "progress": 0.0
  }
}
```

Точки реализации в Kensetsu: `app/routes.py::_encode_internal_single`,
`_encode_internal_batch`, `app/models/job.py::Job`, `Job.to_dict()` и слой
сохранения/восстановления заданий. Внешний исходник и временная копия остаются
разными полями. Не менять существующую политику доступа к внутренним путям.

## Зафиксировать существующий контракт статусов

`GET /api/jobs/<job_id>` уже существует. Документировать значения:

- `planned` — создано и ожидает начала;
- `in_progress` — обрабатывается;
- `done` — финальный результат записан после необходимых remux/metadata шагов;
- `error` — выполнение завершилось ошибкой, причина в `error_message`;
- `cancelled` — задание остановлено.

`progress` — проценты 0–100. Даты — UTC ISO 8601 с `Z`.
`completed_at` само по себе не означает успех: проверять `status`.
Сохранять текущие имена состояний; ALTT адаптируется к этому контракту.
Долгое кодирование не удерживает исходный HTTP POST открытым.

## Полезное добавление: доступность результата

Добавить в job JSON:

- `output_available`: boolean — `status == done` и финальный результат является
  доступным обычным файлом;
- `download_url`: относительная ссылка `/api/jobs/<job_id>/download` при
  доступном результате, иначе `null`;
- `output_size_bytes`: размер доступного результата, иначе `null`.

При удалённом результате возможны `status: done` и `output_available: false`:
история успешного выполнения сохраняется, ссылка на отсутствующий файл не
предлагается. Для старых заданий доступность можно вычислять при GET.
Новые поля не требуют полного чтения или хеширования видео.

До этого дополнения ALTT может проверить доступность через существующий HEAD
download endpoint. Поэтому отдельный webhook не является условием интеграции.

## Следующее улучшение: внешняя идемпотентность

Принять необязательный `request_id` в `/api/internal/encode` и сохранять его с
отпечатком запроса и квитанцией. Повтор того же ID с теми же параметрами возвращает
те же job IDs без нового копирования, создания или запуска заданий. Другие
параметры с тем же ID дают HTTP 409. Сохранение должно переживать рестарт;
конкурирующие одинаковые запросы создают один набор заданий.

Для запроса, ответ на который потерян, предусмотреть read-only получение
квитанции по request_id. Согласовать endpoint и поведение «ещё обрабатывается»
до реализации клиента ALTT. Нынешний ALTT request_id хранится локально и пока
не передаётся Kensetsu: поддержка этого поля требует согласованной доработки
обоих проектов. Не переотправлять unknown автоматически до внедрения контракта.

## Приёмка

1. Single и batch возвращают input_path для каждого успешного задания; пробелы,
   Unicode, квадратные скобки и точный исходный путь сохраняются.
2. Два одинаковых имени в разных каталогах однозначно сопоставляются по input_path.
3. В частичном HTTP 207 успехи и ошибки сопоставляются с нужными входными путями;
   перестановка jobs не меняет сопоставление.
4. `planned → in_progress → done` доступно через существующий GET; ошибка и
   остановка имеют отдельные конечные состояния. После финального remux
   доступность и download endpoint согласованы.
5. Для удалённого выходного файла output_available=false и download_url=null.
6. При внедрении request_id: конкурентный повтор и повтор после рестарта не
   создают дубли, несовпадающий запрос с тем же ID получает 409.

## Что меняется в ALTT

Локальное исправление квитанции разрешает exact filename echo только для одного
фактически отправленного файла и при отсутствии противоречивого полного пути.
В batch сопоставление по basename по-прежнему запрещено. Каноническая локальная
идентичность источника `(info_hash, relative_path)` сохраняется.

Для старой квитанции есть локальная утилита повторного разбора сохранённого
ответа. Она не обращается к Kensetsu и не отправляет файл повторно. После
доставки новой версии ALTT в контейнер предварительный просмотр:

```sh
docker compose -f docker-compose.unraid.yml exec api \
  python scripts/repair_encoder_receipts.py --submission-id 2
```

Если preview показывает правильный file ID и job ID, применить ту же команду
с `--apply`. Исходный ответ, время отправки, snapshot и request_id сохраняются.
Неопределённые результаты таймаутов, противоречия и неоднозначные batch не
исправляются по догадке.

ALTT реализует read-only отслеживание GET статусов: состояние выполнения
хранится в encoder_jobs отдельно от приёма, активные задания опрашиваются
каждые 30 секунд, конечные — каждые 5 минут. Потеря связи/404 и ошибка кодирования
различаются; история показывает прогресс, даты, свежесть проверки и ссылку на
результат. Lease/token защищают обновления от конкурирующих или старых ответов.
Для новых job JSON используется output_available; legacy требует HEAD.
Миграция 0027 восстанавливает доказуемые старые single-квитанции без повторного
POST и заполняет наблюдения из сохранённых external_job_ids.

Поддержка внешнего request_id/GET квитанции при потерянном POST на стороне ALTT
остаётся отдельным улучшением: текущий локальный request_id и защита от
повторной отправки сохраняют прежний контракт. Статусы выполнения не изменяют
sticky ui_status, pipeline и появление HEVC-раздачи.
