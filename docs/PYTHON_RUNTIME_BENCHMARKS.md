# Проверка производительности Python 3.14 → 3.15

> Обновление решения, 13.10.2026: для основного проекта выбран прямой переход
> на обычный CPython 3.15.0. Ниже сохранены результаты и состояние завершённого
> эксперимента; прежнее решение оставить 3.14 относится к его моменту. Текущие
> изменения и проверка рабочего образа — [PYTHON_315_MIGRATION.md](PYTHON_315_MIGRATION.md).
> Переход на 3.15t и экспериментальный HEVC-пул не принят.

## Решение: оставить production на Python 3.14

Функциональная совместимость исправленного Python 3.15-кандидата подтверждена,
но условие миграции «без ухудшения производительности» не подтверждено:
**финальный native Linux benchmark имеет итог `inconclusive` по p95**.
Неопределённость не считается допуском. Дополнительные повторы ради получения
желательного результата не выполняются. Production Dockerfile не меняется.

Локальные median-показатели в целом благоприятны. Они не заменяют проверку хвоста
задержек, ресурсов и целевого окружения. Все три независимые серии сохранены
отдельно; выбросы не удалялись и наборы не объединялись.

## Область проверки

`backend/scripts/benchmark_runtime.py` сравнивает интерпретаторы на фиксированных
локальных операциях AL Torrent Tools. Контроллер использует стандартную библиотеку,
каждое измерение запускает отдельный процесс выбранного интерпретатора.

Проверяются реальные функции приложения:

- AVC/HEVC pairing: 128 релизов, история архивов, exact/missing/overdue,
  несовпадение web-типа, reupload, ignore, новый файл и правка ярлыка;
- JSON каталога и `torrents_fingerprint`: 200 торрентов;
- Jinja2-фрагмент `ignore_hevc_toggle.html`: 400 строк;
- EBML Attachments: 24 вложения по 64 KiB, payload пропускается настоящим парсером;
- `hash_file_blake3`: 64 MiB, чанк 4 MiB, локальный файл в файловом кеше;
- отдельный запуск процесса с импортом этих доменных модулей.

Это **не** тест PostgreSQL, qBittorrent, внешних HTTP-сервисов, скорости кодирования
Kensetsu, Unraid-массива или промышленной нагрузки. В pairing используются
`SimpleNamespace` с метаданными, без стоимости SQL/ORM hydration. Startup означает
новый процесс и импорты доменных модулей, не запуск lifespan API/worker. Время
полного pytest учитывается отдельно и не заменяет эти измерения.

## Протокол и пороги, заданные до измерений

Одинаковые исходники копируются в временный snapshot без `.env`, данные создаются
детерминированно, дочерний env очищается. Сохраняются SHA256 кода/fixtures,
полный список версий зависимостей, версия и параметры сборки интерпретатора,
архитектура, состояние GIL/JIT. Если версии зависимостей различаются, сравнение
останавливается с `blocked_dependency_mismatch`.

Основной запуск: 2 прогревочных процесса на runtime/workload, 16 пар измерений,
минимальная целевая длина одной выборки 250 ms. Итерации калибруются на baseline
и затем одинаковы у обоих интерпретаторов. Внутри каждого процесса дополнительно
выполняются 3 прогревочных итерации. Порядок A/B и B/A чередуется, порядок workload
перемешивается с фиксированным seed. Сборки Python, pytest и другие нагрузочные
проверки во время измерений не запускаются.

Сохраняются все выборки, median/p95/min/max/CV, wall time и CPU time.
`ru_maxrss` переводится в байты с учётом macOS (байты) и Linux (KiB): это high-water
mark **всего** процесса с импортами/setup, не дополнительная память функции и не
idle RSS долгоживущего сервиса. `tracemalloc` запускается отдельно, без искажения
временных выборок, и учитывает только отслеживаемые Python-аллокации.

Сравнивается median парных отношений candidate/baseline. 95%-й доверительный
интервал оценивается percentile bootstrap с 10 000 повторов и фиксированным seed:

- время/CPU: заранее объявленная граница шума +3%;
- peak RSS: отдельная граница +5%;
- верхняя граница CI не выше порога: `non_regressing_within_declared_margin`;
- нижняя граница CI выше порога: `regression`;
- CI пересекает порог: `inconclusive` — не разрешение на миграцию.

Совпадение checksum результатов обязательно. Небольшой шумовой допуск не является
доказательством буквально нулевого замедления; результаты и интервалы следует
рассматривать отдельно от разрешения production-миграции.

## Воспроизведение

Из `backend/`:

```sh
python scripts/benchmark_runtime.py \
  --runtime baseline=/private/tmp/altt-python-runtime-eval/venv314/bin/python \
  --runtime candidate=/private/tmp/altt-python-runtime-eval/venv315/bin/python \
  --source-backend /private/tmp/altt-python-runtime-eval/benchmark-source/backend \
  --repeats 16 --warmups 2 --target-sample-sec 0.25 \
  --output ../docs/runtime_benchmark_314_315_macos_arm64.json
```

Для одной доступной версии используйте один `--runtime`; такой отчёт получает
`baseline_only` и не считается сравнением 3.14 → 3.15. Для production-решения
нужно повторить на целевой системе Linux/архитектуре и воспроизводимой сборке
Docker с её нативными библиотеками и зависимостями.

## Результат

Измерения выполнены 13 октября 2026 года на macOS 27.0.1 / arm64, 10 logical CPU.
Сравнивались CPython **3.14.8 → 3.15.0**, две локальные source PGO-сборки Clang 21,
GIL включён, JIT выключен. Это сравнение production minor-версии из README/Dockerfile
с кандидатом, а не сравнение установленного локального Python 3.13.2 с 3.15.
Все 46 версий установленных дистрибутивов совпали; `_decimal` у обоих использует
native libmpdec 2.5.1, OpenSSL 3.6.3. Параметры сборок и ограничения native libraries
описаны в [проверке совместимости](PYTHON_315_COMPATIBILITY.md).

Полные данные, включая все 16 пар и provenance:
[runtime_benchmark_314_315_macos_arm64.json](runtime_benchmark_314_315_macos_arm64.json).
Snapshot был зафиксирован до реализации истории Kensetsu; его manifest сохранён
в JSON. Все checksum результатов совпали между версиями и всеми выборками.

Median парного изменения wall time (отрицательное число означает быстрее),
95%-й bootstrap CI отношения 3.15/3.14:

- новый процесс + доменные импорты: **−0.76%**, CI **0.96678–1.00865**;
- HEVC pairing: **−2.51%**, CI **0.96622–0.98459**;
- JSON + fingerprint: **−10.70%**, CI **0.88384–0.90079**;
- Jinja fragment: **−0.73%**, CI **0.98362–1.00161**;
- EBML attachments: **−0.90%**, CI **0.98240–0.99937**;
- BLAKE3 + кешированное чтение: **−0.43%**, CI **0.98887–1.00267**.

CPU time: соответственно **−1.07%, −2.55%, −10.74%, −0.73%, −0.88%, −0.34%**.
Эффект JSON/fingerprint и median HEVC подтверждён сильнее, чем небольшие различия
startup/Jinja/BLAKE3, интервалы которых включают отсутствие изменения.

Peak RSS всего процесса: startup **+1.31%**, HEVC **+1.58%**, JSON **+0.55%**,
Jinja **−2.54%**, EBML **−1.79%**, BLAKE3 **+3.81%**. Например, median RSS BLAKE3
вырос с **77.77 MiB до 80.68 MiB**, около **+2.91 MiB**. Эти увеличения находятся
внутри заранее объявленного ресурсного порога 5%, но это **не нулевое увеличение
памяти**. Отдельные `tracemalloc` peaks практически совпали: BLAKE3 около 8.13 MiB
на обеих версиях; они не учитывают всю нативную память процесса.

**Вариативность:** у HEVC на 3.15 сохранён один выброс из 16: wall time 361 ms,
CPU 306 ms при median wall 259 ms. Wall p95 вырос с 272 ms до 289 ms (**+6.43%**),
CV с 1.48% до 9.64%. Выброс не удалялся. Это не отменяет результата median gate,
но небольшой набор не позволяет подтвердить отсутствие регрессии tail latency
или установить причину выброса. Другие workload CV wall time составили около
0.9–3.5%. Host loadavg до/после: 3.65/3.32 (1 minute), на 10 CPU; агенты не
запускали параллельные сборки, pytest или другие нагрузочные проверки.

Итог исходного локального gate по **median wall/CPU и RSS**:
`non_regressing_within_declared_margins`. При строгом требовании «никакого ухудшения любых
метрик» результат не является разрешением: RSS некоторых процессов вырос,
HEVC p95 хуже, tail latency требует более длинного наблюдения.

Этой серии недостаточно для production-миграции: Darwin arm64 не подтверждает
поведение Linux amd64 на Unraid (и отдельно Linux arm64), текущий local MediaInfo
24.12 ниже обязательного production 26, Docker/реальные external services этим
benchmark не проверялись. Для перехода нужен повторный допуск на целевой архитектуре
с production native libraries и образом. Этот документ не меняет Python/Dockerfile.

## Независимая проверка p95 и ресурсов

После исходной серии назначена отдельная подтверждающая серия из **64 пар**
HEVC и BLAKE3. Первая серия и её выброс сохраняются отдельно, данные не объединяются
для устранения выброса. Число итераций фиксировано из первой серии: HEVC **24**,
BLAKE3 **7** на выборку; это сохраняет гранулярность измерения.

До запуска подтверждающей серии зафиксированы дополнительные критерии:

- median wall/CPU: верхняя граница 95% CI отношения не выше **1.03**;
- p95 wall/CPU: верхняя граница 95% CI отношения p95 не выше **1.03**;
- RSS: верхняя граница 95% CI парного median отношения не выше **1.05**;
- для RSS отдельно публикуются парная median разница в MiB и её 95% CI;
- пересечение границы означает **неопределённо**, а не допуск к миграции.

Для p95 bootstrap выбирает совпадающие индексы пар, затем пересчитывает p95
обоих runtime и их отношение, 10 000 повторов. Даже 64 выборки дают ограниченное
число наблюдений хвоста; интервал является локальной оценкой, не гарантией SLA
живого сервиса. `--gate-p95` включает критерий p95 в итоговый gate.

Для воспроизведения к основному вызову выше применяются параметры:

```sh
--workload hevc_pairing --workload blake3_cached_file_io \
--iterations-from ../docs/runtime_benchmark_314_315_macos_arm64.json \
--gate-p95 --repeats 64 \
--output ../docs/runtime_benchmark_314_315_macos_arm64_confirmatory.json
```

При повторном использовании итераций контроллер проверяет совпадение manifest
исходников и версии fixtures. Несовпадение native stdlib/библиотек фиксируется
отдельно; даже успешный timing gate не превращает такой набор в допуск.

Результат независимой серии:
[runtime_benchmark_314_315_macos_arm64_confirmatory.json](runtime_benchmark_314_315_macos_arm64_confirmatory.json).
Все 64 пары сохранены; SHA256 источников совпал с исходной серией.

- HEVC median wall **−2.15%**, CI **0.97365–0.98399**; median CPU **−2.18%**.
  Wall p95 **−1.14%**, CI **0.96396–1.00707**; CPU p95 **−0.95%**,
  CI **0.96453–1.00434**.
- BLAKE3 median парного wall отношения **−0.095%**, CI **0.99565–1.00411**;
  median CPU **−0.074%**. Wall p95 **+0.89%**, CI **0.96165–1.02415**;
  CPU p95 **+0.51%**, CI **0.96620–1.02430**.
- RSS HEVC **+0.945 MiB**, 95% CI **+0.805…+1.219 MiB** (парное отношение +1.06%);
  BLAKE3 **+2.781 MiB**, CI **+2.594…+2.875 MiB** (парное отношение +3.55%).
  Увеличения памяти измеримы, хотя находятся внутри объявленного порога 5%.

Серия подтверждает **median и p95 non-inferiority в пределах 3%** на локальном
arm64 и RSS в пределах 5%. Она не доказывает буквальное отсутствие любого
замедления: например, CI BLAKE3 p95 включает небольшое ухудшение. Вторая серия
не отменяет первый HEVC-выброс; это независимый набор с более устойчивой оценкой
хвоста. Wall CV HEVC baseline/candidate **3.61%/2.70%**, BLAKE3 **3.26%/2.91%**.

Итоговые решения по локальной серии: median **допуск в пределах порога**,
p95 **допуск в пределах порога**, ресурсы **допуск в пределах порога с измеримым
увеличением RSS**. При требовании строго нулевого замедления/увеличения памяти
результат остаётся **неопределён/не выполнен**, а не автоматически разрешён.

Production-кандидат стандартного `python:3.15-slim` отдельно заблокирован
несовпадением native `_decimal`/PyYAML с 3.14-образом; локальная source-сборка
не устраняет этот deployment blocker. Допуск целевого Linux amd64/Unraid ещё
не получен. Окончательное решение учитывает Linux-серию ниже:
**общий допуск к миграции не получен; production-версию не менять.**

## Финальная native Linux arm64 серия

На финальном снимке реализации истории Kensetsu выполнены **32 пары всех шести
workload** с двумя прогревочными проходами и включённым p95 gate. Итерации заново
калибровались на Linux baseline: HEVC 24, JSON 853, Jinja 120, EBML 662, BLAKE3 3.
Калибровка является оценкой целевого времени, фактическая длина выборок сохранена.
Старые macOS counts/SHA не использовались.

Данные: [runtime_benchmark_docker_3147_3150_linux_arm64.json](runtime_benchmark_docker_3147_3150_linux_arm64.json).
SHA256 manifest финальных исходников:
`e443f1ad9d45a4920deed466228450a094a3596e4d0cbc2cde8e506b88086ef3`.
После измерений расширена маскировка ключей `api_key`/`X-Api-Key` в истории
Kensetsu, дополнен тест и исправлено подтверждение повтора в JS: журнал не обходит
общую защиту accepted, смешанный accepted/unknown явно показывает оба количества.
Измеренный `final-backend` snapshot не переписывался; benchmark workloads/runtime
и их checksum этими изменениями не затронуты. Redaction-снимок прошёл по 949 тестов
на обеих Docker-версиях с PostgreSQL. После последнего JS-изменения текущий checkout
прошёл по 946 тестов на обеих host-версиях (3 PostgreSQL-теста пропущены); Node
проверил синтаксис и сценарии подтверждения accepted, mixed и запрета sending.

В одном disposable Docker-контейнере запущены отдельные процессы:

- baseline **Python 3.14.7** из действительного `python:3.14-slim`;
- candidate **Python 3.15.0**, временная исправленная native-сборка;
- native aarch64, Linux 6.12.76-linuxkit, glibc 2.41, GCC 14.2.0, PGO+LTO,
  GIL включён, JIT выключен;
- native `_decimal`/libmpdec 2.5.1, LibYAML 0.2.5, OpenSSL 3.5.7,
  системная MediaInfo 26.10, одинаковые 47 installed distributions;
- совпали checksum всех результатов, версии зависимостей и проверяемая native-среда.

Контейнер не перезапускался между пробами: startup time относится к новому Python
процессу, без Docker start overhead. Сеть отключена; PostgreSQL, qB и HTTP не
используются. Это Linux VM Docker Desktop на arm64, **не Unraid amd64**.
У 3.15 штатные CFLAGS дополнительно содержат frame-pointer flags; это сохранённая
разница реальных сборок, а не доказанная причина вариативности.

Ниже изменения 3.15/3.14 в процентах; CI в скобках — 95% bootstrap интервал
**отношения**. Median — median парных отношений, p95 — отношение p95 выборок.

- **HEVC:** median wall **−0.34%** (0.97966–1.01540), CPU **−0.35%**

- **JSON/fingerprint:** median wall **−5.90%** (0.93061–0.94525), CPU **−5.90%**

- **Jinja:** median wall **+0.65%** (0.99691–1.01982), CPU **+0.64%**

- **EBML:** median wall **−1.98%** (0.97485–0.98583), CPU **−1.99%**

- **BLAKE3:** median wall **+0.29%** (0.99326–1.01718), CPU **+0.29%**

Отдельные RSS-показатели (парный median, absolute 95% CI):

- startup **−0.410 MiB**, CI **−0.410…−0.400**, отношение −0.51%,
  ratio CI **0.99493–0.99506**;
- HEVC **−0.305 MiB**, CI **−0.307…−0.297**, отношение −0.38%,
  ratio CI **0.99619–0.99631**;
- JSON **−0.520 MiB**, CI **−0.520…−0.514**, отношение −0.95%,
  ratio CI **0.99047–0.99058**;
- BLAKE3 **+0.480 MiB**, CI **+0.477…+0.492**, отношение +0.66%,
  ratio CI **1.00656–1.00677**; увеличение измеримо, но внутри порога 5%;
- Jinja и EBML: зафиксировано одинаковое lifetime high-water **29.48 MiB**
  во всех процессах. Такой floor, возможный при fork/exec контроллера,
  ограничивает чувствительность метрики: это не доказательство одинаковой
  дополнительной памяти функций. Python allocations отдельно представлены

Wall CV baseline/candidate: startup **7.82%/19.64%**, HEVC **3.46%/6.36%**,
JSON **4.93%/2.45%**, Jinja **3.80%/9.45%**, EBML **3.40%/2.92%**,

сборки и pytest с измерениями не совмещались. Вариативность сохранена в данных,
причину выбросов этот benchmark не устанавливает.

**Решения отдельно:** корректность — подтверждена тестами из compatibility report;
median wall/CPU — внутри 3%; p95 wall/CPU — **неопределённо**;
наблюдаемый RSS — внутри 5% с указанными ограничениями;
production migration — **не разрешена, остаёмся на 3.14**.

### Воспроизведение Linux-кандидата

Точные входы сборки, constraints, wrapper и инструкции сохранены в
[runtime-eval/README.md](runtime-eval/README.md); их SHA256 и image IDs — в
