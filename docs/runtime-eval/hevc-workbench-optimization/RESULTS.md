Оптимизация подготовки HEVC workbench — результаты 17 октября 2026 года.

На CPython 3.15t с естественно выключенным GIL и C-реализацией psycopg
оптимизация увеличила пропускную способность при четырёх клиентах на
**37,62%**, 95% CI **+34,31…+41,36%**: 4,899 → 6,742 запр./с.
Медиана задержки снизилась с **733,75 до 525,59 мс**, CPU приложения на ответ —
с **685,35 до 444,37 мс** (−35,16%). На обычном 3.15 при C4 выигрыш составил
**13,19%** по пропускной способности, CI +10,62…+15,88%.

После оптимизации 3.15t при C4 обрабатывает в **2,0449 раза** больше запросов,
чем обычный 3.15 с тем же кодом и драйвером (CI 1,9881…2,0993).
Цена — **на 42,65% больше CPU на ответ**: 444,37 против 311,51 мс;
среднее использование CPU — 2,996 против 1,027 ядра. При одном клиенте
3.15t уступает обычному 3.15: медиана выше на **7,14%**, пропускная способность
ниже на **9,82%**. Собственное масштабирование оптимизированного 3.15t C4/C1 —
2,413 раза, при росте медианы с 355,81 до 525,59 мс. Эти результаты поддерживают
оптимизацию сервиса; выбор free-threaded runtime зависит от конкурентной
нагрузки и допустимого расхода CPU.

В отдельной серии на оптимизированном сервисе и C-драйвере MiniJinja не дал
подтверждённого выигрыша. Для 3.15t/C4 оценка изменения пропускной способности
составила **−3,73%**, CI **−7,14…+0,31%**: 6,662 → 6,413 запр./с;
медианы — 536,58 и 555,52 мс. Интервал включает отсутствие эффекта, поэтому
подтверждённой регрессией это также не является. В остальных трёх конфигурациях
интервалы изменения пропускной способности тоже включают ноль.
Миграцию шаблонизатора ради ускорения этого HTTP-сценария данные не обосновывают.
Числа этой отдельной серии не подменяют Jinja-результаты before/after выше.

Абсолютные результаты основной серии с C-реализацией psycopg приведены ниже
парами baseline → optimized. CPU указан в миллисекундах процессорного времени
приложения на ответ; ядра — CPU/wall; RSS — средний RSS процесса после sample.

Обычный 3.15, **C1**: median/p95 **342,85/379,26 → 332,09/346,66 мс**;
**2,862 → 3,098 запр./с**; CPU **330,43 → 292,76 мс/ответ**;
**0,946 → 0,907 ядра**; RSS **179,63 → 236,74 МиБ**.

Обычный 3.15, **C4**: median/p95 **1232,54/1454,04 → 1147,35/1305,30 мс**;
**2,913 → 3,297 запр./с**; CPU **355,19 → 311,51 мс/ответ**;
**1,035 → 1,027 ядра**; RSS **217,13 → 251,97 МиБ**.

3.15t GIL-off, **C1**: median/p95 **401,78/429,98 → 355,81/369,25 мс**;
**2,475 → 2,794 запр./с**; CPU **386,83 → 328,82 мс/ответ**;
**0,957 → 0,919 ядра**; RSS **353,49 → 350,37 МиБ**.

3.15t GIL-off, **C4**: median/p95 **733,75/1000,51 → 525,59/729,46 мс**;
**4,899 → 6,742 запр./с**; CPU **685,35 → 444,37 мс/ответ**;
**3,358 → 2,996 ядра**; RSS **359,07 → 374,20 МиБ**.

RSS/HWM описывают весь процесс после setup, прогрева и проверки результата.
Перед каждым sample прогреваются четыре worker threads, включая измерения C1.
Это не peak памяти одного вызова сервиса. Общего снижения RSS данные не
показывают; оптимизация не заявляется как экономия памяти.

Отдельный контроль с pure psycopg сохранил положительный эффект оптимизации:
пропускная способность выросла на 16,94%/19,44% для обычного 3.15 C1/C4 и
на 21,25%/27,04% для 3.15t C1/C4. Его абсолютные времена сильно отличаются:
например, ordinary C4 median 27376,09 → 22952,30 мс, FT C4 —
5152,63 → 4064,18 мс. Это самостоятельная серия с собственными парными
раундами. Между pure- и C-сериями причинный эффект замены драйвера и его CI
не оценивались; результаты нельзя объединять или переносить на production
psycopg-binary как измеренный коэффициент ускорения.

В production изменён только `backend/app/services/hevc_workbench.py`, SHA-256
`e5838d5cef83af43407130d12e9d6044773e5a459186b2b4f70944054af51ef4`.
SQLAlchemy Rows заменены локальными NamedTuple-контейнерами для многократного
чтения полей. Файловый SELECT сохраняет все raw hash/path для исторического
pairing, а остальные поля материализует только для активных AVC через CASE;
неиспользуемый file.release_id из проекции исключён. Сохраняются история,
правила matching/SLA, receipts, порядок, counts, ready pagination и проверки
видимых файлов. Общий cache, изменения схемы и бизнес-правил не добавлены.

Стоимость преобразования также существует: на fixture создаются 43 392
файловых и 5248 архивных NamedTuple-контейнера на вызов, всего 48 640.
Это копии контейнеров с исходными значениями, без глубокого копирования данных.
Профили с C-драйвером по-прежнему выделяют построение file keys/pairing,
повторный разбор type/quality, Path и сборку строк workbench как следующие
области исследования. Фазовые wall timings включают tracing, ожидание,
компиляцию SQL, fetch/декодирование, hydration и аллокации. Остаток после
вычитания DBAPI execute не является чистым временем fetch. cProfile и фазовые
проходы используются для диагностики, их длительности не заменяют HTTP-замеры.

Детерминированный cProfile на обычном 3.15/C1 с pure psycopg зафиксировал
**554 956 → 511 564** вызова `get_value` и **554 948 → 311 876** вызовов
`ctypes.string_at`: последнее — **−43,8% вызовов**, а не доля CPU или
объяснение всего ускорения. Исходные JSON внутри raw archive:
`diagnostics/baseline-regular-c1.json` и
`diagnostics/optimized-regular-c1-ast.json`.

В отдельных фазовых проходах с C-драйвером файловый SELECT с материализацией
занял **73,16 → 110,86 мс** на обычном 3.15 и **178,61 → 144,19 мс** на
3.15t; построение pairing/file keys — **284,39 → 244,38 мс** и
**350,04 → 286,11 мс** соответственно. Это wall timings под tracing:
pairing остаётся заметной работой, но разнонаправленные изменения файловой
фазы не устанавливают причину HTTP-эффекта. Эти числа не объединяются с pure
cProfile. Raw JSON: `diagnostics/baseline-regular-c1-c.json`,
`diagnostics/optimized-regular-c1-c.json`,
`diagnostics/baseline-ft_off-c1-c.json` и
`diagnostics/optimized-ft_off-c1-c.json`.

Отдельный PostgreSQL EXPLAIN выявил серверную цену CASE. На одном read-only
repeatable-read snapshot оба SELECT обработали **43 392 строки** при
**2048 активных hash**. После одного прогрева каждого варианта четыре пары
AB/BA дали median server execution **5,348 → 18,246 мс**, то есть +12,898 мс
и 3,41 раза; median planning — **0,018 → 0,2955 мс**. Сохранены все десять
планов, включая прогревы; SHA SELECT совпадают с профилями. Это последовательная
диагностика с накладными расходами EXPLAIN, без CI. Она исключает обычную
передачу строк, DBAPI decoding и Python hydration и не измеряет server CPU.
Снижение CPU приложения не включает эту дополнительную работу PostgreSQL;
общую стоимость системы по одной метрике app CPU оценивать нельзя.

Проверки выполнены до сравнительных измерений. Полный suite дал **1523 passed,
0 skipped** в каждой из четырёх конфигураций: ordinary/free-threaded ×
pure/C psycopg, с подключённой изолированной PostgreSQL для соответствующих
интеграционных тестов. Exact differential проверил **40 сценариев × 6
комбинаций драйвера/режима = 240 сравнений, 480 вызовов сервиса**; все вложенные
значения, типы и порядок совпали. Дополнительно прошли **162 HTML/DOM-проверки**
рендереров. Доказательства SQL подтверждают отсутствие writes/flushes/commits
при чтении workbench. GIL проверялся при импортах и в request worker threads;
GIL-off не форсировался. FT с `-X gil=1` использовался только как correctness
control. C-драйвер собран из закреплённого psycopg-c 3.3.6 без native patches;
его upstream FT-поддержка остаётся
[экспериментальной](https://github.com/psycopg/psycopg/issues/1095).

Три независимые серии содержат **192 samples / 1536 timed HTTP responses**:
по 8 раундов × 8 запросов для восьми конфигураций в каждой серии. Порядок
AB/BA и runtime/concurrency групп сбалансирован; выбросы не удалялись.
95% CI получены 5000 paired block bootstrap-перевыборками целых раундов,
seed 315017. Медианы/p95 объединяют 64 latency observations на конфигурацию;
p95 остаётся исследовательской оценкой хвоста. Пропускная способность —
суммарные ответы / суммарный batch wall. Context wall пересекается с HTTP wall,
его медианы нельзя складывать как независимые фазы.

Среда: CPython 3.15.0 ordinary/free-threaded, PGO/LTO, JIT выключен;
psycopg 3.3.6 и system libpq 17.11. Linux ARM64 в Docker Desktop: 10 CPU,
7,65 GiB RAM; PostgreSQL 16.15; fixture **1024 releases / 5248 archives /
43 392 files**. Измерялся исходный ASGI route live partial вместе с SQL,
подготовкой данных, проверками видимых файлов, рендером и HTMLResponse.
TCP/TLS, браузерный JavaScript, настоящий SSE/HTMX swap и внешние сервисы
в performance-серии не участвовали. Это не production psycopg-binary и не
native Unraid AMD64; измерения не устанавливают их задержки и масштабирование.
