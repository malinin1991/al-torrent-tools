# Выбор хранилища после согласования улучшений

Дата: 2026-10-13. Контекст: обычный CPython 3.15, личный Unraid, приоритет HEVC и Kensetsu.

## Решение для текущей реализации

Сохраняем PostgreSQL 16. Замена БД не входит в согласованные пункты 1–3 и 5.

Рабочая схема уже использует связи и внешние ключи для заданий/логов, pipeline/событий, файлов и квитанций; уникальность для дедупликации; транзакции; advisory locks между процессами. API, worker и два профиля ботов могут конкурировать за одни объекты. Условные UPDATE и резервирование строк непосредственно нужны текущим исправлениям.

Разнородные payload и снимки параметров уже сохраняются в JSONB. PostgreSQL позволяет сочетать эту гибкость с реляционными ограничениями. Официальная документация: [JSONB](https://www.postgresql.org/docs/16/datatype-json.html), [блокировки](https://www.postgresql.org/docs/16/explicit-locking.html), [SKIP LOCKED для очередей](https://www.postgresql.org/docs/16/sql-select.html).

MongoDB поддерживает многодокументные транзакции, но для них требуется replica set или sharded cluster; standalone не поддерживается. Это не означает обязательность нескольких машин для любого тестового запуска replica set и не означает отсутствия транзакций в MongoDB. Источник: [MongoDB 8.0: consistency with transactions](https://www.mongodb.com/docs/v8.0/data-modeling/enforce-consistency/transactions/).

Для этого проекта переход потребовал бы переработки ORM, миграций, запросов, связей, ограничений и протоколов конкурентного владения, а затем переноса и проверки истории. Выигрыш в скорости от такой замены не измерялся. Из текущих проблем такой переход не следует: они устраняются корректным использованием существующего хранилища.

## Когда вернуться к вопросу

При измеренном ограничении PostgreSQL, которое нельзя разумно устранить запросами, индексами, разделением нагрузки или конфигурацией, либо при существенной смене модели продукта. Сам по себе большой JSON-ответ внешнего API не является основанием для миграции.
