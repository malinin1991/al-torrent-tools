# Python 3.15 и 3.15t: отдельный эксперимент

> Обновление решения, 13.10.2026: для основного проекта выбран прямой переход
> на обычный CPython 3.15.0. Ниже сохранены результаты и состояние завершённого
> эксперимента; прежнее решение оставить 3.14 относится к его моменту. Текущие
> изменения и проверка рабочего образа — [PYTHON_315_MIGRATION.md](PYTHON_315_MIGRATION.md).
> Переход на 3.15t и экспериментальный HEVC-пул не принят.

> Уточнение приоритета после эксперимента: пользователь предпочитает меньшее
> время ожидания долгих операций, даже ценой большего CPU time и RAM.
> Ресурсные пороги ниже сохраняют исходный протокол измерений; теперь они
> диагностические и сами по себе не блокируют полезную оптимизацию.
> Выигрыш HEVC compute около 19% поэтому рассматривается как полезный
> кандидат. На тестовом наборе один проход по 128 релизам занимал около
> 10.7 ms на исходном regular и 8.8 ms на t-off с рефакторингом: экономия
> около 1.9 ms. Ускорение целой долгой операции с БД/рендерингом ещё нужно
> измерить; проценты этого короткого расчёта его не доказывают.

## Итог: точечный выигрыш HEVC, общий переход не выполнен

Эксперимент завершён. Во всех трёх режимах прошли по **1011 тестов** с PostgreSQL;
GIL сохранялся включённым/включённым/выключенным после полного прогона.
На общем pure-backend контракте не обнаружены ошибки импорта, auto-GIL fallback
или расхождения результатов. Производительность не является универсальным
улучшением: t-off замедлил JSON примерно на 11%, Jinja на 20%, startup на 21%.

Изолированный рефакторинг HEVC с созданием снимка и постоянным пулом четырёх
потоков на t-off уменьшил median wall time относительно исходной функции на
regular 3.15 на **19.00%** (95% CI отношения **0.80160–0.82989**). Цена:
CPU time **+98.24%**, lifetime peak RSS **+36.22%**, или **+28.484 MiB**.
Это ускорение вычислительного пути без SQL, рендеринга и внешнего кодирования.
Production остаётся на 3.14; экспериментальный helper не подключён к рабочим
call sites. Отсутствие регрессии всего сервиса не подтверждено.

## Область и контракт

Сравниваются три режима одного minor/release: обычный CPython 3.15.0,
free-threaded CPython 3.15.0 с GIL и free-threaded CPython 3.15.0 с GIL,
выключенным штатно. Это отдельный эксперимент, не изменение production Python
и не повторная оценка уже принятого решения оставить 3.14.

**Production-контракт целиком не воспроизведён:** для закреплённого
`psycopg-binary==3.3.6` не найден совместимый Linux arm64 `cp315t`/`abi3t` wheel
или sdist. Проверяется отдельно нормализованный контракт: одинаковая версия
`psycopg==3.3.6`, pure-Python backend и системный libpq во всех трёх режимах,
остальные версии зависимостей и проверяемые native libraries одинаковы.
Это не эквивалент production binary backend. Если такой контракт тоже не
проходит native/GIL audit, остаётся явно ограниченный pure-compute эксперимент
на одинаковых зависимостях; небезопасный режим не замеряется.

Runner: `backend/scripts/benchmark_free_threading.py`. Экспериментальный adapter:
`backend/scripts/hevc_parallel_experiment.py`. Production их не импортирует.
Adapter фиксирует метаданные в immutable snapshot, разделяет работу по релизам,
восстанавливает private dictionaries внутри задачи и вызывает неизменённый
`find_unpaired_avc`. Session, ORM-объекты, shared mutable JSON в пул не передаются.

**Не применяется** `PYTHON_GIL=0` или `-X gil=0` поверх неподдерживаемых extensions.
Используются обычный runtime, `3.15t` с явным GIL-on и `3.15t` с его default.
Каждый дочерний процесс проверяет GIL до импорта, после импорта, после прогрева
и после работы. Автоматическое включение GIL блокирует эту выборку; она не
выдаётся за GIL-off. Отдельный metadata audit импортирует native stdlib,
PyYAML и выбранный psycopg/libpq backend.

## Протокол, заданный до измерений

Одинаковые sources фиксируются snapshot без `.env`/данных; app/helper manifest,
версии зависимостей, native libraries, build/GIL/JIT flags и SHA256 обоих
benchmark drivers сохраняются в JSON. Дочерний env очищен, БД в вычислениях
не используется, сети/реальных qB, AniLiberty, Telegram и Kensetsu нет.
Для интерпретации 4 threads сохраняются cgroup `cpu.max`, `cpu.stat`, effective
cpuset, affinity и memory limit до/после измерений: одного `os.cpu_count()`
недостаточно. GIL state сохраняется у каждой успешной выборки на всех границах.

План — **12 сбалансированных троек** на каждый case. Шесть порядков
ABC/BCA/CAB/ACB/CBA/BAC повторяются два раза: каждый режим равное число раз
занимает каждую позицию, порядок пар сбалансирован. Порядок cases перемешивается
с фиксированным seed. Есть отдельный прогревочный проход и 3 внутренних прогрева
в каждом новом процессе. Сборки и pytest с замерами не совмещаются.

Калибровка на обычном 3.15 целится в 150 ms выборки. Все HEVC cases используют
**одно и то же число полных вычислений**, выбранное по исходному алгоритму:
не увеличиваем работу одного варианта ради его более красивого throughput.
Данные: 128 релизов, восемь доменных сценариев, default 32 релиза на задачу,
четыре непересекающихся chunks, один фиксированный UTC clock.

Адаптация ограничена калибровкой длительности и пропуском несовместимых
режимов/cases. Число повторов фиксировано; нет повторов «до успеха», изменения
данных ради выигрыша или искусственного CPU-цикла вместо доменных операций.
Ожидаемое измерительное окно — несколько минут, не полный повтор длительных
сборок и test suites.

Сначала сравниваются прежние шесть локальных путей: startup/imports,
исходный HEVC pairing, JSON/fingerprint, Jinja fragment, EBML attachments,
64 MiB BLAKE3 с локальным кешированным I/O.

Затем на **том же HEVC алгоритме и объёме данных**:

- исходный `find_unpaired_avc` до refactor;
- snapshot evaluation `workers=0`: последовательный тот же refactor/chunks/thaw;
- cold pool с 1/2/4 threads: создание и shutdown пула включены в каждый вызов;
- hot pool с 1/2/4 threads: один пул процесса после прогрева, snapshot уже готов;
- snapshot creation + cold evaluation с 0/4 workers: включает стоимость границы,
  но не SQL/ORM hydration, web rendering и внешнее I/O.

Hot pool и готовый snapshot — отдельный потенциальный compute-выигрыш при
повторном использовании. Текущий ALTT не получает такой режим автоматически.
В рамках одного релиза история AVC/HEVC остаётся единой, а не разбивается
по произвольным торрентам; это сохраняет SLA anchors и pairing semantics.

## Метрики и интерпретация

Сохраняются все выборки, median/p95/min/max/CV, wall throughput в operations/sec,
CPU time и среднее число занятых CPU cores (`cpu_time / wall_time`), peak RSS.
RSS корректируется по единицам macOS/Linux и включает lifetime imports/setup;
fork/exec floor может скрывать небольшую разницу лёгких workloads.
На Linux дополнительно сохраняются `/proc/self/status` VmHWM и RSS после работы,
чтобы lifetime `ru_maxrss` не выдавался за точную дополнительную память функции.

Парные сравнения отделяют эффекты:

- regular → 3.15t GIL-on: стоимость free-threaded build при сохранённом GIL;
- 3.15t GIL-on → GIL-off: эффект режима на одной сборке;
- regular → 3.15t GIL-off: практическое сравнение вычислительного пути;
- original → sequential refactor: стоимость/эффект изменения представления;
- sequential refactor → 1/2/4 threads: scaling при одинаковом алгоритме;
- cold → hot: влияние повторного использования пула;
- original → snapshot+compute: не прячем сериализацию и cold pool overhead.

95% CI — 10 000 paired bootstrap resamples: median парного отношения,
для p95 — совпадающие индексы пар с пересчётом p95 обоих вариантов. CI speedup
получается обратным отношением wall time. CPU-cost и CPU-utilization показываются
отдельно: больше занятых cores само по себе не означает меньше CPU time.

До измерений сохранены прежние диагностические границы: **+3% median/p95 wall
и CPU time**, **+5% RSS**. Верхняя граница CI не выше порога — результат внутри
порога; нижняя выше — регрессия; пересечение — неопределённо. CPU core ratio
описательный, не «регрессия» только из-за распараллеливания. Диагностические
границы не являются разрешением production-миграции или обещанием строго
нулевого ухудшения. У 12 выборок оценка p95 ограничена; широкие CI публикуются.

Рост throughput чистого HEVC не равен ускорению API/worker или кодирования.
Текущий сервис часто ждёт SQL, qB, HTTP, hashing и внешнего Kensetsu; эти расходы
эксперимент не измеряет. Linux arm64 в Docker Desktop также не подтверждает
поведение целевого Unraid/Linux amd64.

## Результаты основной серии

Исходные данные: [runtime_benchmark_315_vs_315t_linux_arm64.json](runtime_benchmark_315_vs_315t_linux_arm64.json).
Завершены все 12 сбалансированных троек для 15 cases; blockers отсутствуют,
checksums совпали. Native environment и все 46 distributions одинаковы.
GIL проверен в каждой выборке до/после imports, warmup и work.
Linux CPU affinity/cpuset — 0–9, cgroup `cpu.max = max 100000`: quota не ограничена.
Сборки и тесты с измерениями не совмещались.

Median парного изменения времени t-off относительно regular 3.15 и 95% CI
отношения (отрицательное изменение означает быстрее):

- Startup/process+imports: **+20.83%**, CI **1.18311–1.23610**; p95 **+41.53%**,
  CI **1.12852–1.74012**. Подтверждённая регрессия.
- Исходный HEVC: **−0.89%**, CI **0.96676–1.00131**; p95 **−0.79%**,
  CI **0.97292–1.01166**. В пределах диагностического порога, нулевой эффект
  также совместим с данными.
- JSON/fingerprint: **+11.43%**, CI **1.10793–1.11927**; p95 **+13.43%**,
  CI **1.09666–1.17017**. Подтверждённая регрессия.
- Jinja: **+19.96%**, CI **1.18171–1.23736**; p95 **+26.15%**,
  CI **1.16624–1.32579**. Подтверждённая регрессия.
- EBML: **+3.73%**, CI **1.02427–1.04947**; p95 **+3.18%**,
  CI **1.01819–1.05678**. Неопределённо относительно границы +3%.
- BLAKE3 cached I/O: **−0.78%**, CI **0.96920–1.00534**; p95 **−3.75%**,
  CI **0.94955–0.99803**. В пределах диагностического порога.

GIL-on t-build также сохраняет повышенное потребление памяти; он не становится
обычным runtime. Все его сравнения с regular и t-off, CPU/p95/RSS, полные
выборки и доверительные интервалы находятся в JSON и интерактивном отчёте.

В основной серии HEVC использовал 14 полных расчётов по 128 релизам на выборку.
Описательные median wall times одной выборки, без создания snapshot:
исходный regular **153.97 ms**, исходный t-off **152.24 ms**; новый
последовательный refactor t-off **173.81 ms**; hot2 t-off **95.89 ms**;
hot4 t-off **72.10 ms**. Hot4 занимает в среднем около **3.43 CPU cores**,
но CPU time возрастает до **247.29 ms**. Это compute-only выигрыш, примерно
вдвое по сравнению с исходным regular, а не ускорение страницы целиком.

Свежий snapshot + cold4 t-off: **149.34 ms**, CPU **345.19 ms**. На regular
тот же cold-путь занимает **221.88 ms**. Подготовка и управление потоками
существенны; переносить только compute-hot цифру на приложение нельзя.

RSS после работы из `/proc/self/status` в основной серии: исходный HEVC
regular **80.07 MiB**, t-off **101.30 MiB**, hot4 t-off **108.04 MiB**.
Это наблюдение после вычисления, не idle RSS сервиса. Lifetime peak и VmHWM
публикуются отдельно: inherited floor особенно заметен на лёгких cases.

## Дополнительный путь: snapshot + hot pool

До его измерения отдельно назначена короткая серия: **12 сбалансированных троек**,
исходный HEVC против **свежего snapshot + persistent hot pool с 4 threads**.
Она дополняет отсутствующий путь: compute-only hot pool исключает snapshot cost,
а основной snapshot+compute case использует cold pool. Данные основной серии
сохраняются отдельно и не заменяются новым набором.

Runner `backend/scripts/benchmark_free_threading_hot.py` использует тот же frozen
app/helper manifest и **14 полных HEVC вычислений на выборку**, зафиксированных
основной серией. `--iterations-from` проверяет manifest и сохраняет SHA256
исходного отчёта. Snapshot создаётся внутри каждого измеряемого вызова, повторно
используется только executor. Пороги median/p95/ресурсов остаются прежними.
Измеренная версия основного runner сохранена в `runtime-eval/315t/`.

Дополнительная серия также завершена без blockers и расхождения checksums:
[raw hot E2E](runtime_benchmark_315_vs_315t_hot_e2e_linux_arm64.json),
[отдельный парный анализ](runtime_benchmark_315_vs_315t_hot_e2e_analysis.json).
Manifest app/helper и 14 вычислений на выборку совпали с основной серией;
исходный main JSON сохранил SHA-256
`7aa68fa51c2100a5a10cd6d8ba5df894977276d0301e04b8027eb7e841123f61`.
Выборки двух серий не объединялись.

Практическое сравнение **original regular → fresh snapshot + hot4 t-off**
внутри этой дополнительной серии:

- Median wall: **−19.00%**, ratio CI **0.80160–0.82989**; throughput
  **1.2345×**, CI **1.2050–1.2475×**.
- P95 wall: **−21.78%**, ratio CI **0.75523–0.81578**.
- CPU time: **+98.24%**, ratio CI **1.95497–2.02325**; CPU p95
  **+91.35%**, CI **1.85010–1.99162**.
- Lifetime peak RSS: **+36.22%**, ratio CI **1.35394–1.36489**;
  **+28.484 MiB**, absolute CI **+27.820…+28.688 MiB**.
- Среднее использование CPU — около **2.44 cores** вместо одного;
  это объясняет уменьшение задержки при увеличении общей стоимости CPU.

Эффект рефакторинга **внутри t-off** (original → fresh snapshot + hot4):
median wall **−16.52%**, CI **0.80988–0.84031**; p95 **−18.84%**,
CI **0.80270–0.82855**. CPU **+104.37%**, CI **1.98489–2.05222**;
peak RSS **+6.38%**, **+6.430 MiB**, CI **+5.943…+6.750 MiB**.
На regular и t GIL-on этот же snapshot/pool путь медленнее исходной функции.

Точечные проценты выше — median парных отношений. Они могут отличаться от
отношения двух отдельно округлённых median времени. Значения p95 при 12
наблюдениях имеют ограниченную устойчивость; приведённые CI описывают эту
локальную серию, а не SLA живого сервиса.

## Воспроизведение

Сначала собрать изолированные образы и выполнить import/GIL audit по
[runtime-eval/315t/README.md](runtime-eval/315t/README.md). Полный production
binary stack не подменять результатами pure-backend эксперимента. Зафиксировать
свой backend snapshot без `.env`/данных и выбрать новые имена output, сохраняя
исходные отчёты. Команды ниже — из корня проекта, пути заменить своими:

```sh
docker run --rm --network none --entrypoint /opt/runtime-modes/run_regular.sh \
  --mount type=bind,source="$PWD/backend/scripts",target=/bench/scripts,readonly \
  --mount type=bind,source=/private/tmp/altt-python-runtime-eval/ft-eval-final-backend,target=/bench/source/backend,readonly \
  --mount type=bind,source="$PWD/docs",target=/bench/output \
  altt-python-eval:315-vs-315t-pure-20261013 /bench/scripts/benchmark_free_threading.py \
  --runtime regular=/opt/runtime-modes/run_regular.sh \
  --runtime ft_on=/opt/runtime-modes/run_t_gil1.sh \
  --runtime ft_off=/opt/runtime-modes/run_t_default.sh \
  --source-backend /bench/source/backend --scope common-python-backend \
  --repeats 12 --warmups 1 --target-sample-sec 0.15 \
  --output /bench/output/315t-main-rerun.json
```

Для независимой hot-E2E серии использовать те же mounts/image/wrappers,
заменив script на `/bench/scripts/benchmark_free_threading_hot.py` и добавив:

```sh
--iterations-from /bench/output/315t-main-rerun.json \
--output /bench/output/315t-hot-e2e-rerun.json
```

Для аудита первоначально измеренного main driver сохранён
`runtime-eval/315t/benchmark_free_threading.main-measured.py`; последующее
расширение CLI поддерживает reuse counts для дополнительной серии. SHA256
driver и parent driver записаны в отчётах. При повторении пересмотреть native
версии, effective GIL, CPU quotas и manifest; прежний verdict автоматически
не переносится на новую сборку/хост.

Сводный вывод: **параллельный HEVC возможен и даёт локальный выигрыш задержки,
но общего допуска к t-миграции нет**. Перед production-пулом приоритетнее
убрать повторный полный pairing одного snapshot внутри запроса, затем измерить
реальную страницу, SQL и ресурсы на целевом Unraid amd64. Подробности ownership,
native/I/O и найденных ограничений — в
[PYTHON_315T_OPTIMIZATION.md](PYTHON_315T_OPTIMIZATION.md).
